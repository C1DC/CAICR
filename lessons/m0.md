## 1 · What Cybersecurity Really Is — for an Organisation

Forget the hoodie-in-a-dark-room picture. For a bank, a hospital, a ministry or a
telco, **cybersecurity is the practice of protecting the information and systems
the organisation depends on — and the people, money and trust behind them — from
accidental and deliberate harm.** It is a *business* problem that happens to be
technical, not an IT department chore.

Every organisation runs on three things being true about its data and systems:

| Property | Plain meaning | What it looks like when it breaks |
|----------|---------------|-----------------------------------|
| **Confidentiality** | Only the right people can see it | Customer records dumped on Telegram |
| **Integrity** | It is correct and unaltered | A fraudster changes a payment beneficiary |
| **Availability** | It is there when needed | Ransomware locks the core banking system |

Professionals call these the **CIA triad**, and add two more that matter in
practice: **Authenticity** (the message/person really is who they claim — the
heart of fraud and BEC) and **Non-repudiation / Continuity** (you can prove what
happened, and you keep operating through disruption).

::: key | The one idea to carry all week
Security is not about stopping "hackers" for its own sake. It is about keeping the
organisation **able to do its job, legally and with its reputation intact**, even
when things go wrong. A breach is not an IT incident — it is lost money, broken
law, and broken trust.
:::

::: ghana | Why this is urgent in Ghana
Banks, fintechs, Mobile Money, hospitals and government portals now hold the
records and the money of millions of Ghanaians. The **Cybersecurity Act, 2020
(Act 1038)** and the **Data Protection Act, 2012 (Act 843)** make protecting them
a *legal duty*, with the Cyber Security Authority (CSA) and mandatory incident
reporting. The question is no longer "if" an institution is targeted — it is
"when", and "will the people inside know what to do".
:::

## 4 · The Language You Need

Security has a vocabulary. Learn these now and nothing this week will sound like
jargon. Keep this table handy — the full glossary lives in `labctl reference
glossary`.

| Term | Plain meaning |
|------|---------------|
| **Asset** | Anything worth protecting — data, a server, money, a reputation |
| **Threat** | Something that could cause harm (a hacker, malware, a flood, a careless insider) |
| **Threat actor** | The *who* behind a threat — criminal gang, state, hacktivist, insider |
| **Vulnerability** | A weakness that a threat can exploit (unpatched software, weak password) |
| **Exploit** | The specific technique or code that takes advantage of a vulnerability |
| **Risk** | The chance a threat exploits a vulnerability × how bad the impact is |
| **Attack surface** | The sum of all the ways in — every exposed service, login, person |
| **Malware** | Malicious software (viruses, worms, trojans, spyware) |
| **Ransomware** | Malware that encrypts your files and demands payment to unlock them |
| **Phishing** | Tricking people via email/SMS into clicking, paying, or giving credentials |
| **Spear-phishing / BEC** | Phishing aimed at a specific person; **Business Email Compromise** impersonates an executive/supplier to redirect payment |
| **Social engineering** | Hacking the *human*, not the machine — persuasion and deception |
| **Credential** | A username + password (or key/token) that proves who you are |
| **MFA** | Multi-Factor Authentication — a second proof (code/app) so a stolen password isn't enough |
| **Zero-day** | A vulnerability with no patch yet — unknown to the vendor |
| **Patch** | A fix that closes a vulnerability; "patching" is applying it |
| **APT** | Advanced Persistent Threat — a skilled, well-resourced attacker who stays hidden for a long time |
| **IOC** | Indicator of Compromise — evidence an attack happened (a bad IP, file hash, domain) |
| **TTPs** | Tactics, Techniques & Procedures — *how* an attacker operates (see MITRE ATT&CK) |
| **Payload** | The part of an attack that does the damage once it's in |
| **C2** | Command & Control — the attacker's remote channel to control infected machines |
| **Lateral movement** | Spreading from the first machine to others inside the network |
| **Privilege escalation** | Going from a normal user to admin/root |
| **Incident vs Breach** | An **incident** is any security event; a **breach** is a confirmed loss/exposure of data |
| **SOC** | Security Operations Centre — the team/room that watches for and responds to attacks |
| **SIEM** | The system that collects logs and raises alerts for the SOC |
| **Defence in depth** | Layered controls, so one failure doesn't mean game over |
| **Zero Trust** | "Never trust, always verify" — treat every request as if it came from a hostile network |

## 5 · How Attacks Really Happen — and the Tools Attackers Use

**A typical institutional breach, step by step:**

1. **Recon** — the attacker learns about you from the outside: exposed servers,
   staff names, leaked passwords. (You'll do this in M1 and with OSINT tools.)
2. **Initial access** — they get in through the easiest door: a **phishing** email
   that steals a password, an **exposed service** (RDP, an old web app), or
   **stolen/reused credentials** bought online.
3. **Foothold** — they run code on one machine and make sure they can get back in.
4. **Privilege escalation** — they turn a normal account into **admin/root** (you
   do exactly this in the RT lab with a `sudo` misconfiguration).
5. **Lateral movement** — they hop to more machines, hunting for the crown jewels.
6. **Objective** — they do what they came for: deploy **ransomware**, steal data,
   or commit **fraud** (redirect a payment, drain Mobile Money).

::: case | Real patterns used against institutions like yours
- **Business Email Compromise (BEC):** a look-alike email "from the CEO" tells
  finance to pay a new supplier account. No malware — pure deception. Billions lost
  globally each year. *(You investigate one in M5.)*
- **Ransomware on a hospital:** phishing → foothold → the whole patient system is
  encrypted; care stops until backups are restored. *(Resilience — M6, M8.)*
- **Exposed RDP / weak password:** an admin port left open to the internet, a
  guessable password — the single most common ransomware entry point.
- **Mobile Money / SIM-swap fraud:** social engineering a telco agent to take over
  a phone number, then draining wallets and resetting bank logins.
- **Deepfake fraud:** in 2024 a finance worker paid out **US$25m** after a video
  call with a deepfaked "CFO" and colleagues. AI makes deception scalable. *(M7.)*
:::

**The tools attackers use — which you will learn to use *and* defend against:**

| Stage | Tools attackers use | You learn it in |
|-------|---------------------|-----------------|
| Recon / OSINT | **Nmap**, **Shodan**, **Maltego**, theHarvester | M1, Tools |
| Initial access | **Gophish** (phishing), look-alike domains, exposed services | RT, M5 |
| Exploitation | **Metasploit**, **sqlmap**, public exploit code | RT, M4 |
| Credential theft | **Mimikatz**, **hashcat**, **John the Ripper** | M3 |
| Command & Control | **Cobalt Strike**, Sliver (criminal C2 frameworks) | M6 (detection) |
| Lateral movement | **BloodHound**, built-in Windows tools | Tools |
| Impact | Ransomware-as-a-Service, info-stealers | M6, M8 |

## 9 · The Command Line, and Why It Is Non-Negotiable

A graphical interface shows you what someone *decided* to show you. The command
line shows you **everything**, exactly, and lets you combine small tools into
powerful investigations. Security work is about precision and evidence: the
terminal gives you both, and it scripts and repeats. Every serious tool in this
field is driven from it.

The shell prompt tells you who and where you are:

```The shell prompt
┌──(kali㉿kali)-[~]
└─$
```

`kali@kali` is *user@host*; `~` is your current directory (your home folder); `$`
means a normal user (a `#` would mean root). **Read the prompt before you type.**

## 10 · The Linux Command Line — the Commands That Matter

Work through these at the terminal. Each block is real; type them, don't just read
them. Everything here you will use again in the labs.

### 5.1 Who and where am I?

```Terminal — identity and location
whoami              # your username
id                  # your user id, groups (shows if you have sudo/root power)
hostname            # the machine's name
pwd                 # "print working directory" — where you are right now
uname -a            # kernel and architecture — know the system you're on
date                # current date/time (matters for evidence timestamps)
```

A security professional *always* knows which account they are using and on which
host. Acting as the wrong user, on the wrong box, is how mistakes and incidents
happen.

### 5.2 Getting help — the habit that makes you self-sufficient

```Terminal — read the manual
man nmap            # the full manual for a command (press q to quit, / to search)
nmap --help         # quick option summary
whatis grep         # one-line description
apropos password    # find commands related to a keyword
```

Nobody memorises every flag. Professionals read the manual fast — `man` is your
first move with any unfamiliar tool.

### 5.3 Moving around the filesystem

Linux is a single tree starting at `/` (root). Everything hangs off it.

```Terminal — navigate the tree
ls                  # list files here
ls -la              # long listing, including hidden files (names starting with .)
ls -lh              # human-readable sizes (K, M, G)
cd /etc             # change to an absolute path
cd ..               # up one level
cd ~                # home;  cd -  returns to the previous directory
tree -L 2           # a visual tree, two levels deep
```

Paths are **absolute** (start with `/`, e.g. `/etc/passwd`) or **relative** (from
where you are, e.g. `../logs`). `.` is here, `..` is the parent, `~` is home.

### 5.4 Reading files

```Terminal — read and inspect files
cat notes.txt               # dump a whole file
less /var/log/syslog        # page through a big file (q to quit, / to search)
head -n 20 file             # first 20 lines
tail -n 20 file             # last 20 lines
tail -f /var/log/auth.log   # follow a log live as it grows — vital in IR
file evidence.img           # what KIND of file is this, really?
strings binary.bin          # pull readable text out of a binary (find URLs, keys)
xxd capture.bin | head      # raw hex view — forensics bread and butter
```

`file`, `strings` and `xxd` are the ones beginners skip and professionals live on —
they tell you what something actually is when the extension lies.

### 5.5 Creating, copying, moving, deleting

```Terminal — manage files and folders
mkdir -p cases/2026/incident-07   # make nested directories in one go
touch report.md                   # create an empty file / update its timestamp
cp -r evidence/ evidence-copy/     # copy (work on COPIES, never originals)
mv draft.md final.md               # move or rename
rm file.txt                        # delete a file
rm -rf folder/                     # delete a folder and everything in it
```

::: warning | `rm -rf` is irreversible
It asks no questions and there is no recycle bin. Read the path **twice** before
you press Enter — especially as root.
:::

### 5.6 Finding things

```Terminal — locate files and content
find /home -name "*.pcap"             # by name, anywhere under /home
find . -type f -mtime -1              # files modified in the last day (IR triage)
find / -perm -4000 -type f 2>/dev/null  # setuid binaries — classic priv-esc hunt
which nmap                            # where a command lives on disk
grep -r "password" /etc/ 2>/dev/null  # search file CONTENTS recursively
```

`find` and `grep -r` are how you locate a needle — a leaked credential, a recently
changed file, a dangerous permission — in a haystack of thousands of files.

```Terminal — chain and capture
cat auth.log | grep "Failed password" | wc -l     # count failed SSH logins
nmap -sV 10.13.3.0/24 > scan.txt                   # save output to a file
```

### 5.8 Text processing — turning data into answers

```Terminal — filter, cut, count, sort
grep -i "error" log        # -i ignore case
grep -E "T10[0-9]{2}" f    # -E extended regex (match ATT&CK IDs like T1046)
grep -v "healthcheck" log  # -v invert: everything EXCEPT matches
grep -c "fail" log         # -c count matching lines
cut -d',' -f1,3 data.csv   # pull columns 1 and 3 from a CSV
sort file | uniq -c | sort -rn   # count duplicates, most-frequent first
awk '{print $1}' access.log | sort | uniq -c   # top source IPs from a log
sed 's/old/new/g' file     # stream-edit: replace text
wc -l file                 # count lines
```

::: key | Memorise this pattern
`sort | uniq -c | sort -rn` — *"what are the most common values?"* — is one of the
most useful lines in all of security analysis. It is how you find the one source IP
behind a thousand alerts.
:::

### 5.9 Permissions and ownership

Every file has an owner, a group, and three permission sets — for the **owner**,
the **group**, and **everyone else** — each granting read (`r`), write (`w`) and
execute (`x`).

```File permissions, decoded
ls -l script.sh
# -rwxr-xr--  1  kali  kali  ...  script.sh
#  │└┬┘└┬┘└┬┘
#  │ │  │  └ others: read only
#  │ │  └─── group: read + execute
#  │ └────── owner: read + write + execute
#  └──────── type: - file, d directory, l link
```
```Terminal — change permissions and ownership
chmod +x labctl        # make a file executable
chmod 640 secret.txt   # owner rw, group r, others none  (4=r 2=w 1=x)
chmod 600 id_rsa       # private keys MUST be owner-only, or SSH refuses them
chown kali:kali file   # change owner and group (usually needs sudo)
umask                  # the default permissions mask for new files
```

Permissions are a security control in their own right. A world-readable
`config.php` with a database password in it — which you will find in Module 4 — is
a permissions failure.

### 5.10 Users, privilege and sudo

```Terminal — privilege and accounts
sudo <command>     # run one command as root (you'll be asked for your password)
sudo -l            # what am I allowed to run as root? (attackers check this)
su - username      # switch to another user
cat /etc/passwd    # the list of accounts on the system
who ; last         # who is logged in now; login history
```

Root (uid 0) can do anything. Use `sudo` deliberately, never habitually —
over-use of root is how a small mistake becomes a catastrophe.

### 5.11 Processes and services

```Terminal — what is running
ps aux                 # every running process (a = all, u = detailed, x = incl. daemons)
ps aux | grep ssh      # is sshd running?
top        (or htop)   # live process/resource monitor (q to quit)
kill 1234              # stop process id 1234 politely
kill -9 1234           # force-kill (last resort)
jobs ; fg ; bg         # manage jobs you backgrounded with &
nohup long-task &      # keep a task running after you log out
systemctl status docker # the state of a system service
sudo systemctl start docker
```

In incident response, `ps aux` is often your first look at *what is actually
running* on a suspect machine — including the thing that should not be.

### 5.12 Networking from the terminal

```Terminal — inspect the network
ip a                  # your network interfaces and IP addresses (modern)
ip r                  # the routing table
ping -c 4 10.13.3.10  # is a host reachable? (4 packets)
ss -tulpn             # listening TCP/UDP ports and the processes behind them
dig example.com MX    # query DNS (Modules 1 & 5)
host example.com      # quick DNS lookup
whois example.com     # domain registration details
curl -I https://site  # fetch just the HTTP response headers
curl -s https://site/api | less   # fetch a page/API quietly
wget https://site/file           # download a file
nc -lvnp 4444         # netcat: listen on a port (the Swiss-army knife of networking)
```

`ss -tulpn` answers *"what is this machine exposing to the network?"* — the single
most important question when you harden a server. You will use `dig`, `whois` and
`curl` directly in the labs.

### 5.13 Packages — installing tools

### 5.14 Archives, transfer and integrity

```Terminal — archive, decode, verify
tar -czf case.tar.gz case/      # create a compressed archive
tar -xzf case.tar.gz            # extract one
zip -r out.zip folder/ ; unzip out.zip
base64 -d artifact.b64          # decode Base64 (Module 6)
sha256sum evidence.img          # fingerprint a file — proof of integrity
sha256sum -c evidence.sha256    # verify it hasn't changed
```

`sha256sum` is the backbone of chain of custody in Module 6 — a hash proves, with
mathematics, that evidence was not altered.

### 5.15 System and disk

```Terminal — system and storage
df -h          # disk space per filesystem, human-readable

uptime         # how long the system's been up, and load
lsblk          # block devices / disks (useful before imaging in forensics)
```

### 5.16 History, shortcuts and speed

```Terminal — history and variables
history          # your command history
!!               # repeat the last command (e.g. sudo !!)
!$               # the last argument of the previous command
echo $PATH                 # the directories searched for commands
export TARGET=10.13.3.10   # set a variable for this session
echo $TARGET
```

Learn these keystrokes — they pay off every single day:

- **Tab** — auto-complete commands and paths (use it constantly).
- **Ctrl‑R** — reverse-search your history (type a few letters of an old command).
- **Ctrl‑C** — cancel the running command.
- **Ctrl‑L** — clear the screen (same as `clear`).
- **Ctrl‑A / Ctrl‑E** — jump to the start / end of the line.
- **Ctrl‑D** — end of input / log out.
- **↑ / ↓** — previous / next command.

## Check yourself

1. **You need the five most frequent source IPs in a web log's first column. Write
   the one-liner.**
   → `awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5`.

2. **`ls -l` shows `-rw-------` on `id_rsa`. Good or bad, and why?**
   → Good — a private key must be readable only by its owner (`600`). SSH will
   refuse a key that others can read.

3. **What does `ss -tulpn` tell you, and when is it your first command?**
   → The listening TCP/UDP ports and the processes behind them — your first command
   when assessing what a machine exposes to the network.

4. **Why do forensic examiners run `sha256sum` before and after handling
   evidence?**
   → To prove mathematically that the evidence was not altered — the foundation of
   chain of custody.

5. **A colleague asks you to "just quickly scan" a partner company's website to
   check it's secure. Your response?**
   → No — not without that company's **written** authorisation. Scanning a third
   party is an offence under Act 1038, regardless of good intentions.

## Glossary

- **Shell** — the program that interprets your commands (Bash/Zsh).
- **Path (absolute/relative)** — a file's location from `/` or from where you are.
- **Pipe `|`** — send one command's output as the next command's input.
- **Redirection `>` `>>` `2>`** — send output/errors to a file.
- **Permissions (rwx)** — read/write/execute for owner, group, others.
- **sudo / root** — run as the all-powerful administrator (uid 0).
- **PATH** — the directories the shell searches for commands.
- **Hash (sha256)** — a file's unique fingerprint, used to prove integrity.
