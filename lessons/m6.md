# Module 6 — Digital Forensics & Incident Response

**Day 3 · Afternoon Session · ~4 hours · Hands-on lab: `labctl start m6`**

When an incident happens the evidence is fragile and the clock is running. A disk
can be overwritten, a running process can be killed, and — most urgently — the
contents of memory vanish the instant someone "just reboots it to be safe". This
module teaches you the disciplines that separate a professional incident
responder from someone who turns a bad day into a catastrophe: preserve what
happened so it stands up later (in court, to a regulator, to your own board),
reconstruct the attack across *disk, memory and logs*, and respond without
destroying the very evidence you need.

The two registers run throughout. The **conceptual** half gives you the
principles (Locard, hashing, chain of custody), the collection order that saves
the perishable evidence first, and the NIST incident-response lifecycle that
keeps a panicked response disciplined. The **practical** half makes you work a
complete evidence package: prove integrity by hashing, recover a *deleted*
credentials file from a disk image, carve a malware command line, C2 address,
in-memory credential and exfiltration address out of a **RAM dump**, decode an
obfuscated dropper, reconstruct the timeline from the authentication log — and
then **correlate it all** into one provable story.

::: outcome | By the end of this module you will be able to
1. Explain **Locard's principle**, cryptographic **hashing** and **chain of custody**, and why they make findings defensible.
2. **Acquire** evidence correctly — write-blocking, `dd`/`dc3dd`, raw vs **E01** — and verify the image hash matches the source.
3. Apply the **order of volatility (RFC 3227)** and run the **NIST SP 800-61 / PICERL** lifecycle without destroying evidence.
4. Examine a disk image with **Sleuthkit/Autopsy**, recover deleted files, explain **slack/unallocated** space and **file carving**, and catch a **timestomp** via MACB.
5. Decode a layered, obfuscated attacker artefact with **CyberChef** or the CLI.
6. Perform **memory forensics** — triage with `strings`/`bulk_extractor` and run the professional **Volatility** workflow (`pstree`/`netscan`/`cmdline`/`malfind`).
7. Know **where the evidence lives on Windows** — Event Logs (4624/4625/4688), Sysmon, prefetch, amcache, Run keys, scheduled tasks, `$MFT`.
8. Reconstruct a **super-timeline** (plaso/log2timeline) and **correlate** disk + memory + logs into one narrative.
9. **Run the response** — containment, eradication of *every* foothold, validated recovery — and execute a **ransomware playbook** (identify, don't pay, check for exfiltration, restore).
10. Recognise and detect **anti-forensics** (timestomping, log clearing), and map the chain to **MITRE ATT&CK**.
:::

## 1 · The Forensic Foundation — Prove You Didn't Change the Evidence

All of forensics rests on one idea: **you can prove, mathematically, that the
evidence is unaltered.** If you cannot, nothing you find is trustworthy. Three
things underpin everything that follows.

- **Locard's exchange principle** — *every contact leaves a trace*. The attacker
  touched the system; artefacts exist; your job is to find and preserve them.
- **Hashing** — a cryptographic hash (SHA-256) is a file's fingerprint. Hash the
  evidence *before* you touch it and *after*; matching hashes prove it is
  unchanged. Change a single byte and the hash changes completely.
- **Chain of custody** — a documented record of who held the evidence, when, why,
  and what they did with it. It is what makes your findings *defensible* to a
  court, a regulator (CSA/DPC) or an insurer.

```Terminal — preserve first, always
sha256sum evidence.img                 # fingerprint the evidence now
sha256sum -c evidence.sha256           # later: prove it STILL matches
```

::: key | Image and hash before you touch anything
You never work on the original. You make an exact **image** (bit-for-bit copy),
hash it, and analyse the *copy* — so the original stays pristine and provable. The
first thing `labctl verify m6` checks is exactly this: that `sha256sum -c` still
passes.
:::

### 1.1 Acquiring the evidence — write-blockers and image formats

*How* you make that image matters as much as that you made it. Two rules:

- **Write-block the source.** A **write-blocker** — hardware (a device between the
  disk and your workstation) or software — guarantees read-only access, so the mere
  act of imaging cannot alter the original. Without it, plugging a disk into a live
  OS updates timestamps and can destroy evidence before you start.
- **Hash as you acquire, verify after.** The image's hash must equal the source's;
  record both in the acquisition log.

Imaging tools and formats:

- **`dd`** writes a **raw** image (exact bytes, no metadata). **`dc3dd`/`dcfldd`**
  are `dd` plus built-in hashing and logging. GUI tools (**FTK Imager**,
  **Guymager**) do the same and can write **E01 / EWF** (Expert Witness Format) —
  compressed, with the acquisition **hash, examiner and case notes embedded** in
  the file. E01 is the courtroom standard; raw `dd` is fine for lab work.

```Terminal — acquire a disk read-only, hashing as you go
dc3dd if=/dev/sdb of=evidence.img hash=sha256 log=acquire.log   # (behind a write-blocker)
sha256sum evidence.img          # must match the source hash recorded in acquire.log
```

RAM disappears the instant the machine powers off — taking with it the running

::: warning | Never "just power it off"
The instinct to reboot or pull the power to "stop the attack" is one of the most
damaging mistakes in incident response — it destroys the single most valuable
evidence there is. You **isolate** a compromised host from the network; you do
**not** power it off. Capture memory first, then disk.
:::

## 3 · The Incident-Response Lifecycle

The standard is **NIST SP 800-61**; the SANS mnemonic is **PICERL**. The phases
are a discipline that stops a frightened team from destroying evidence or
reinfecting clean systems.

| Phase | What you do |
|-------|-------------|
| **Preparation** | Policies, playbooks, a trained team, tested tools — *before* anything happens |
| **Detection & Analysis** | Confirm it is real, scope it, start the evidence timeline |
| **Containment** | Stop the spread *without destroying evidence* (isolate, don't power off) |
| **Eradication** | Remove the attacker — close the vector, reset credentials, kill persistence |
| **Recovery** | Restore from verified-clean backups, validate, reconnect |
| **Post-Incident** | Lessons learned, improve controls, report where required |

## 4 · Disk Forensics

With the image preserved and hashed, examine it. **Autopsy** is the GUI platform
used by law enforcement worldwide; **Sleuthkit** is its command-line engine.

```Terminal — examine a disk image with Sleuthkit
fsstat evidence.img                    # filesystem type + layout (e.g. FAT16)
fls evidence.img                       # list files; a '*' marks a DELETED entry
icat evidence.img 6                    # read a file by its inode (incl. deleted)
tsk_recover evidence.img ./recovered   # carve deleted files back out in bulk
```

Why can "deleted" files be recovered? Deleting a file usually just flags its
directory entry and marks its space free — the **data itself sits on disk
untouched** until something overwrites it. Forensics lives in that gap. In this
lab, `fls` reveals the macro-enabled spreadsheet the user was lured into opening
(`q3invoic.xls`), and `icat` on the deleted inode recovers a **credentials file
containing a VPN password** — remember that password; it reappears in memory.

### 4.1 How deletion really works — and slack space

Every filesystem "deletes" by updating *metadata*, not by erasing data:

- **FAT** flags the directory entry (first byte → `0xE5`) and frees the cluster chain.
- **NTFS** marks the file's **`$MFT`** record unused and clears its bit in the bitmap.
- **ext (Linux)** marks the **inode** free.

In every case the bytes remain until reused — which is why carving works. Two more
places evidence hides: **slack space** (a file smaller than its cluster leaves old
data in the leftover bytes) and **unallocated space** (freed clusters not yet
overwritten). Both routinely hold fragments of deleted documents and credentials.

### 4.2 File carving — recovery without the filesystem

When the metadata is gone (a formatted or damaged disk), you recover by **file
signature** instead — the magic bytes that begin and end each file type — ignoring
the filesystem entirely:

```Terminal — carve files by signature
foremost -t pdf,jpg,doc,xls -i evidence.img -o carved/   # by header/footer
photorec evidence.img                                     # interactive, many types
```

### 4.3 MACB timestamps and timestomping

Every file carries timestamps — **MACB**: **M**odified, **A**ccessed, metadata-
**C**hanged, **B**orn (created). They are the raw material of a timeline. But
attackers **timestomp** — backdating a malicious file so it blends in.

::: key | How to catch a timestomp
On NTFS, the `$MFT` stores **two** timestamp sets: `$STANDARD_INFORMATION` (what
the OS shows, and what timestomping tools change) and `$FILE_NAME` (updated by the
kernel, usually left untouched). When the two disagree — or a file claims it was
"created 2009" inside a folder built in 2026, or a create time *later* than the
modify time — you are looking at a stomp. The anomaly itself is evidence of intent.
:::

## 5 · Decoding Attacker Artefacts

Attackers rarely leave a payload in the clear. They wrap it in layers — Base64,
URL-encoding, hex — to slip past filters and tired eyes. **CyberChef** (the "cyber
Swiss-army knife", usable fully offline) lets you build a decode "recipe" by
dragging operations; the CLI does the same one layer at a time.

```Terminal — peel the layers off a dropper
# CyberChef recipe: From Base64 -> URL Decode  (reveals the C2 URL)
base64 -d suspicious_artifact.txt      # one layer; chain more as needed
```

The decoded artefact reveals the **command-and-control (C2) domain** the dropper
calls home to — and, critically, it should be the *same* C2 host you independently
find in memory. Agreement between two sources is proof.

## 6 · Memory Forensics — The Reward for Not Powering Off

A RAM capture holds what the disk never saw. Full-featured analysis uses
**Volatility**, but a great deal of value falls out of two simpler tools that are
perfect for triage: **`strings`** (extract human-readable text) and
**`bulk_extractor`** (scan a blob and auto-carve URLs, emails, IPs and more into
tidy files).

```Terminal — triage a RAM dump with strings and bulk_extractor
# What malicious process is running? (note the masquerade: svch0st, not svchost)
strings memory.raw | grep -iE 'svch0st|\\temp\\'

# Auto-carve indicators into categorised files
bulk_extractor -o be_out memory.raw
cat be_out/url.txt        # the C2 host the PowerShell stager calls
cat be_out/email.txt      # the exfiltration address

# Plaintext credential living in memory
strings memory.raw | grep -i vpnadmin

# Persistence the malware set up
strings memory.raw | grep -i schtasks
```

From one RAM dump you recover: the **malware** (`svch0st.exe` — a masquerade of
`svchost.exe`, ATT&CK T1036 from Module 3), the **C2 host**, a **plaintext VPN
credential**, the **exfiltration email**, and the **persistence** mechanism (a
scheduled task, `schtasks` / ATT&CK T1053). None of this survives a reboot — which
is the entire reason RFC 3227 puts memory first.

### 6.1 The professional workflow — Volatility

`strings` and `bulk_extractor` are *triage*; the DFIR standard for structured
memory analysis is **Volatility** (now **Volatility 3**), which understands the
operating system's structures and answers precise questions:

| Plugin (Windows) | Answers |
|------------------|---------|
| `windows.pstree` / `pslist` | the process tree — spot the odd child (Word → PowerShell) |
| `windows.psscan` | processes `pslist` can't see — finds **hidden/terminated** ones |
| `windows.netscan` | live network connections — the C2 socket |
| `windows.cmdline` | the **command line** each process was launched with |
| `windows.malfind` | injected / hidden executable code regions |
| `windows.dlllist` / `handles` | loaded DLLs / open files and keys |

```Terminal — the Volatility 3 memory workflow
vol -f memory.raw windows.pstree     # which process spawned the stager?
vol -f memory.raw windows.netscan    # the live C2 connection
vol -f memory.raw windows.cmdline    # the PowerShell one-liner, in full
vol -f memory.raw windows.malfind    # code injected into a trusted process
```

This lab ships a generic RAM blob you triage with `strings`/`bulk_extractor` (no
OS profile needed, works anywhere) — but on a real Windows capture, `pstree` +
`netscan` + `cmdline` is the sequence that turns "something's wrong" into "`winword`
spawned `powershell` which opened a socket to the C2 — here's the exact command".

## 7 · Where the Evidence Lives — Windows DFIR Artefacts

Most incidents you will work are on **Windows**, where the record of what happened
is spread across a known set of artefacts. Knowing *where to look* is half the
job:

| Artefact | Where | What it proves |
|----------|-------|----------------|
| **Security Event Log** | `…\winevt\Logs\Security.evtx` | logons — **4624** success, **4625** failure; **4688** process creation |
| **Sysmon** (if deployed) | its own event log | process creation (**1**), network (**3**), image loads — the gold standard |
| **Prefetch** | `C:\Windows\Prefetch` | that a program **executed**, when, and how many times |
| **Amcache / Shimcache** | registry hives | evidence of execution + full path + (Amcache) a SHA-1 |
| **Registry Run keys** | `…\CurrentVersion\Run` | autostart **persistence** |
| **Scheduled Tasks** | `C:\Windows\System32\Tasks` | persistence — exactly our `schtasks` implant |
| **`$MFT` / USN journal** | NTFS metadata | file create / delete / rename history |
| **LNK files / Jump Lists** | recent-items | which documents the user opened |

Map that onto this lab's story: the **4625** failures then a **4624** success are
the brute force that got in; **prefetch** and **4688** show the macro lure and the
PowerShell stager *executing*; the **Scheduled Tasks** folder holds the persistence.

::: key | You can only read artefacts you kept
Default Windows logging is thin and rolls over fast. **Sysmon plus centralised,
off-box log collection** is what turns "we think PowerShell ran" into "here is the
4688 event with the full command line, shipped to the SIEM before the attacker
could clear it." Deploy it *before* the incident — it is preparation (Module 4's
detection engineering meets this module's forensics).
:::

## 8 · Timeline Reconstruction & Correlation

Individual artefacts are leads; a **timeline** is a case. Logs give you the clock.
In this lab the authentication log (`auth.log`) shows the intrusion's spine:

```Terminal — reconstruct the login timeline from auth.log
grep -E 'Failed|Accepted' auth.log     # failures (brute force) then the success
```

Dozens of `Failed password` lines from one **source IP** (a brute force), then an
`Accepted password` from that *same* IP for a specific account — that is the
moment the attacker got in, with a timestamp.

### 8.1 The super-timeline

One log is a single thread; a **super-timeline** weaves *every* timestamped
artefact — filesystem MACB, Event Logs, prefetch, registry, browser history — into
one chronological view. The standard tool is **plaso / log2timeline**:

```Terminal — build and read a super-timeline
log2timeline.py timeline.plaso evidence.img          # ingest every artefact
psort.py -o l2tcsv timeline.plaso > timeline.csv     # one sorted timeline
```

You then **pivot on the incident window** — zoom to the minutes around a known
event (the macro open) and read what happened immediately before and after: the
document opened, `powershell` executed, a file was written to `\Temp`, a scheduled
task was created. The super-timeline is how scattered artefacts become a minute-by-
minute narrative.

::: key | Correlation is what makes it unarguable
The VPN password you recovered from the **deleted file on disk** is the *same*
password sitting in the **RAM dump** — and the brute-force **source IP** in
`auth.log` is the same one you met in the Module 4 SOC feed. When disk, memory and
logs independently point to the same facts, you no longer have a theory; you have
proof. A responder who correlates writes a report that survives a courtroom; one
who reports a single tool's output writes a guess.
:::

## 9 · Running the Response — Containment, Eradication, Recovery

The lifecycle table (§3) names the phases; here is how you actually execute the
back half under pressure.

**Containment — stop the spread, keep the evidence.** Prefer **network isolation**
(disable the switch port, move to a quarantine VLAN, or use your EDR's host-isolate)
over pulling the cable — and **capture memory first**, because isolation shouldn't
cost you the volatile evidence. The goal is to stop lateral movement and the C2
channel while the host stays alive for analysis.

**Eradication — remove *every* foothold.** Miss one and they are back by morning.
Hunt down and remove the scheduled task, the Run key, any service or web shell;
**reset every credential that touched the box** (here, the harvested VPN password);
and close the entry vector (patch, disable macros, fix the exposed service).

**Recovery — rebuild, restore, validate.** For anything deeply compromised,
**reimage** beats "clean" — you can never fully trust a box an attacker had root
on. Restore data from **verified-clean, offline** backups, validate it works,
monitor closely, *then* reconnect. Ask the hard question out loud: *"are we
certain we are not still compromised?"*

**Roles.** A real response has an **Incident Commander** (decides, owns comms), a
**scribe** (logs every action with a timestamp — that log *is* your chain of
custody), technical leads, and legal/comms. Deciding and recording under pressure
is the skill the capstone (Module 10) tests.

### 9.1 The ransomware playbook (this lab's scenario)

1. **Isolate — do not power off.** RAM may hold the encryption key or the running
   process; capture it first.
2. **Identify the strain** — the ransom note, file extension, or a service like ID
   Ransomware. A *known* strain may have a free decryptor; a novel one will not.
3. **Scope it — and check for exfiltration.** Modern ransomware is **double
   extortion**: data is *stolen before* it is encrypted. Look for the large
   outbound transfer that preceded the encryption — if data left, this is also a
   **breach**.
4. **Do not pay.** Payment funds crime, carries no guarantee of a working key,
   marks you as a payer, and may breach sanctions. It is a last-resort *business*
   decision taken with counsel — never a technical fix.
5. **Recover** from offline **3-2-1** backups; rebuild compromised hosts.
6. **Report if data was exfiltrated** — notification obligations under Act 843
   (DPC) and Act 1038 (CSA) follow (Module 8).

### 9.2 Anti-forensics — and catching it

Attackers try to erase their tracks: **timestomping** (§4.3), **clearing logs**,
encryption and secure-wiping. The tells and the defences:

- A cleared Windows Security log leaves **Event ID 1102** ("audit log was
  cleared") — the act of hiding is itself a loud signal.
- **Ship logs off-box** to a SIEM so clearing them locally erases nothing that
  matters; use **immutable/append-only** storage for evidence.
- Gaps in an otherwise continuous timeline, or a `$STANDARD_INFORMATION` /
  `$FILE_NAME` mismatch, point straight at tampering.

## 11 · Scenarios — When Response Makes It Better, or Worse

::: ghana | Ghana & West Africa
A **2023 West African hospital ransomware** incident became a catastrophe through
three avoidable failures: backups sat on the *same network segment* and were
encrypted too (no offline copy); the IT team **powered the servers off
immediately**, destroying volatile evidence and complicating recovery; and there
was **no tested IR plan**, so everything was improvised under pressure. The
result: a three-week outage and partially unrecoverable patient records. The
antidote is the **3-2-1 backup rule** (3 copies, 2 media types, 1 offline/offsite)
with **restores tested monthly**, plus a plan practised *before* the incident.
:::

::: case | WannaCry (2017) and NotPetya / Maersk (2017, ~US$300M)
**WannaCry** disrupted the UK's NHS, forcing cancelled operations — it spread on
*unpatched* systems, so patching (Modules 2 & 4) is incident response that happens
*before* the incident. **NotPetya**, a destructive wiper masquerading as
ransomware, crippled shipping giant Maersk; their survival hinged on a single
*surviving* backup found by luck. Tested recovery is the difference between a bad
quarter and the end of a business.
:::

::: case | Colonial Pipeline, 2021 — a containment decision with national stakes
The *decision* to shut down operational systems was a **containment judgement
call** that halted fuel to the US east coast. Incident response is as much
disciplined decision-making under pressure as it is technical work — which is why
you rehearse it.
:::

## 12 · The Worked Investigation (what the lab asks of you)

`labctl start m6` gives you a complete, file-based evidence package: a disk image
and its recorded hash, an obfuscated artefact, a RAM dump, and an auth log. Work
it in forensic order:

1. **Integrity.** Prove the image is unaltered (`sha256sum -c`) — this is checked first.
2. **Disk.** Identify the **filesystem** (FAT16), name the **macro lure**
   (`q3invoic.xls`), and `icat`/`tsk_recover` the **deleted credentials file** to
   recover the **VPN password**.
3. **Decode.** Peel the **artefact** back to its **C2 domain**.
4. **Memory.** Carve `memory.raw` for the **malware**, the **C2 host** (it matches
   the decoded artefact), the **in-memory VPN credential** (it matches the disk),
   the **exfil email**, and the **persistence** method.
5. **Timeline.** From `auth.log`, find the **brute-force source IP** and the
   **account** the attacker finally logged in as.
6. **Concepts.** State what the **order of volatility** collects first, and the
   **ATT&CK** technique for the macro→PowerShell execution.

::: warning | Your values are unique
The VPN password, the C2 domain and the exfiltration email are **randomised per
student** — and the lab deliberately makes the disk and memory copies of the VPN
password **match**, so you can demonstrate correlation. The examples here
(`svch0st.exe`, the domains, the emails) are illustrative; report *your* values.
`labctl verify m6` grades against your personal answer key.
:::

Then complete the **chain-of-custody form** and the **incident report**
(`labctl worksheet m6`), mapping each phase of your response to NIST SP 800-61.

## Common mistakes

::: warning | What trips students up
- **Powering off to "stop the attack."** You destroy the RAM evidence — isolate
  from the network instead.
- **Working on the original.** Always image and hash first; analyse the copy.
- **Skipping the hash.** Without before/after hashes you cannot prove integrity.
- **Containment that wipes evidence.** Stop the spread, but preserve the scene.
- **Backups on the same network.** Ransomware encrypts those too — you need an
  offline copy.
- **Reporting artefacts, not a timeline.** The deliverable is the correlated story
  across disk, memory and logs.
:::

## Key takeaways

::: key | Carry these out of Module 6
- **Hash before and after** — mathematical proof the evidence is unchanged;
  **Locard** guarantees the traces exist.
- **Order of volatility (RFC 3227): memory first**, disk later — isolate, never
  power off.
- **Acquire write-blocked**, hash on acquisition and **verify** (raw `dd` / E01).
- **"Deleted" ≠ gone** — recover from the filesystem, from **slack/unallocated**,
  or by **carving**; catch a **timestomp** via the `$MFT` `$SI`/`$FN` mismatch.
- **Memory:** `strings`/`bulk_extractor` to triage, **Volatility**
  (`pstree`/`netscan`/`cmdline`/`malfind`) to prove.
- **Know where Windows keeps evidence** — Event Logs (4624/4625/4688), Sysmon,
  prefetch, amcache, Run keys, scheduled tasks, `$MFT`.
- **Build a super-timeline** and **correlate** disk + memory + logs — matching
  facts across sources turn a theory into proof.
- **Response:** isolate (don't power off) → eradicate *every* foothold → validated
  recovery. **Ransomware:** identify, check for exfiltration, **don't pay**,
  restore from offline **3-2-1** backups.
- **ATT&CK:** macro→PowerShell **T1059.001**; scheduled-task persistence **T1053**.
:::

## Check yourself

1. **You reach a compromised server that's still running. Your instinct is to pull
   the power. Why is that wrong, and what do you do instead?**
   → Powering off destroys volatile memory evidence (processes, injected code,
   keys, plaintext credentials). Isolate from the network, then capture RAM before
   disk.

2. **Hashes match before and after analysis. What has that proven?**
   → That your analysis did not alter the evidence — its integrity and your chain
   of custody hold.

3. **`fls` shows a file marked `*`. What does that mean, and can you read it?**
   → It is deleted; yes — the data usually persists, so `icat`/`tsk_recover` can
   recover it.

4. **You find the same VPN password in a deleted file on disk *and* in the RAM
   dump. Why does that matter?**
   → **Correlation** — two independent sources agreeing turns a lead into proof,
   and ties the disk and memory evidence to the same intrusion.

5. **Containment vs eradication?**
   → Containment stops the spread (isolate) while preserving evidence; eradication
   removes the attacker (close the vector, reset credentials, remove persistence).

6. **The West African hospital's backups failed them. Why, and what rule fixes
   it?**
   → They were on the same network and got encrypted too. The **3-2-1 rule** (one
   copy offline/offsite), with restores tested monthly, fixes it.

7. **A malicious file claims it was created in 2019, but sits in a folder built last
   week. How do you confirm a timestomp on NTFS?**
   → Compare the `$MFT` timestamp sets: timestomping tools change
   `$STANDARD_INFORMATION` but usually not `$FILE_NAME`. A mismatch (or a create
   time later than the modify time) exposes the tampering.

8. **Ransomware has encrypted a bank's file server. Name the first action and the
   one thing you must check before even thinking about recovery.**
   → First: **isolate without powering off** (RAM may hold the key). Check:
   whether data was **exfiltrated before encryption** (double extortion) — if so
   it is also a reportable **breach**, not just an availability incident. And do
   **not** pay.

## Glossary

- **Locard's exchange principle** — every contact leaves a trace.
- **Hash (SHA-256)** — a file's cryptographic fingerprint.
- **Chain of custody** — the documented handling history of evidence.
- **Image (raw / E01)** — a bit-for-bit copy you analyse instead of the original; E01 embeds hash + case metadata.
- **Write-blocker** — hardware/software that makes the source read-only during acquisition.
- **`dd` / `dc3dd`** — raw imaging / imaging with built-in hashing and logging.
- **Order of volatility (RFC 3227)** — collect the most perishable (RAM) first.
- **Slack / unallocated space** — leftover bytes in a file's last cluster / freed space; both hold recoverable data.
- **File carving** — recovering files by signature (foremost/photorec) when the filesystem metadata is gone.
- **MACB / timestomping** — Modified/Accessed/Changed/Born timestamps / backdating them to hide; caught via `$MFT` `$SI`/`$FN` mismatch.
- **Autopsy / Sleuthkit / Volatility** — disk-forensics GUI / CLI / memory-forensics framework (`pstree`, `netscan`, `cmdline`, `malfind`).
- **`strings` / `bulk_extractor`** — extract readable text / auto-carve URLs, emails, IPs from a blob.
- **Windows artefacts** — Event Logs (4624/4625/4688), Sysmon, prefetch, amcache/shimcache, Run keys, scheduled tasks, `$MFT`.
- **Super-timeline (plaso/log2timeline)** — all timestamped artefacts woven into one chronology.
- **CyberChef** — an offline tool for building multi-step decode recipes.
- **NIST SP 800-61 / PICERL** — the incident-response lifecycle.
- **Double extortion** — stealing data before encrypting it, so "we have backups" isn't enough.
- **3-2-1 rule** — 3 copies, 2 media types, 1 offsite/offline.
