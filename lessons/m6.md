# Module 6 — Digital Forensics & Incident Response

**Day 3 · Afternoon · Hands-on lab: `labctl start m6`**

When an incident happens the evidence is fragile and the clock is running. This
module teaches you to preserve what happened so it stands up later — in court, to
a regulator, to your own board — reconstruct it, and respond without making it
worse. These are the disciplines that separate a professional responder from
someone making a bad day catastrophic.

By the end you will be able to:
- preserve evidence with hashing and an unbroken chain of custody;
- examine a disk image, list files and recover deleted ones with Sleuthkit/Autopsy;
- decode an obfuscated attacker artefact;
- run an incident by the NIST SP 800-61 lifecycle without destroying evidence.

---

## 1. The big picture: prove you didn't change the evidence

Forensics rests on one idea: **you can prove, mathematically, that the evidence
is unaltered.** If you cannot, nothing you find is trustworthy. Two principles
and one law underpin everything:

- **Locard's exchange principle** — every contact leaves a trace. The attacker
  touched the system; artefacts exist; your job is to find and preserve them.
- **Hashing** — a cryptographic hash (SHA-256) is a file's fingerprint. Hash the
  evidence *before* you touch it and *after*; matching hashes prove it is
  unchanged. Change one byte and the hash changes completely.
- **Chain of custody** — a documented record of who held the evidence, when, why,
  and what they did. It is what makes findings *defensible*.

## 2. Order of volatility — collect the perishable first

Some evidence vanishes faster than the rest. **RFC 3227** codifies the order:
**memory (RAM) → network state and running processes → disk → archival media.**
RAM disappears the instant you power off — along with running malware, injected
code, and encryption keys. This is why the instinct to "just turn it off and
reboot" is one of the most damaging mistakes in incident response: it destroys
the most valuable evidence there is. You **isolate** a compromised host; you do
not power it off.

## 3. Incident response: the lifecycle

The standard is **NIST SP 800-61** (the SANS equivalent is the mnemonic
**PICERL**): the phases are a discipline that keeps a panicked response from
destroying evidence or reinfecting clean systems.

| Phase | What you do |
|-------|-------------|
| **Preparation** | Policies, playbooks, trained team, tested tools — *before* anything |
| **Detection & Analysis** | Confirm it's real, scope it, start the evidence timeline |
| **Containment** | Stop the spread *without destroying evidence* (isolate, don't power off) |
| **Eradication** | Remove the attacker — close the vector, reset credentials, kill persistence |
| **Recovery** | Restore from verified-clean backups, validate, reconnect |
| **Post-Incident** | Lessons learned, improve controls, report if required |

## 4. How the tools actually work

**Preserve first:**

```
sha256sum evidence.img                 # fingerprint it
sha256sum -c evidence.sha256           # later: prove it still matches
```

**Examine** with **Autopsy** (the GUI platform used by law enforcement worldwide)
or its command-line engine, **Sleuthkit**:

```
fsstat evidence.img                    # filesystem type + layout
fls evidence.img                       # list files; a '*' marks a DELETED entry
icat evidence.img 5                    # read a file by its inode (incl. deleted)
tsk_recover evidence.img ./recovered   # carve deleted files back out
```

Why can "deleted" files be recovered? Deleting usually just marks the space free
and flags the directory entry — the data often sits on disk untouched until
something overwrites it. Forensics exploits that gap.

**Decode** obfuscated artefacts with **CyberChef** (or the CLI). Attackers hide
payloads in layers — Base64, URL-encoding, hex — which you peel back ("From
Base64 → URL Decode") to reveal, say, a command-and-control URL.

```
base64 -d suspicious_artifact.txt      # one layer; chain more as needed
```

**Memory forensics** (demonstrated) uses tools like **Volatility** on a RAM
capture to find running processes, injected code and credentials that never touch
disk — the reward for not powering the machine off.

## 5. An analogy

It is a crime scene. The first officer does not start moving furniture — they
photograph everything, bag and label each item, and log who touched what. A
fingerprint is only evidence if you can show it was not planted or smudged. A disk
image is identical: you make an exact copy, fingerprint it (hash), and work on the
*copy* — never the original — so the original stays pristine and provable. And as
you would take a dying witness's statement first, you capture volatile memory
before it is gone.

## 6. Scenarios — when response makes it better, or worse

### Local (Ghana / West Africa)

- A **2023 West African hospital ransomware** incident turned a problem into a
  catastrophe through three failures: backups sat on the *same network segment*
  and were encrypted too (no offline copy); the IT team **powered the servers off
  immediately**, destroying volatile evidence and complicating recovery; and
  there was no tested IR plan, so the response was improvised under pressure. The
  result: a three-week outage and partially unrecoverable patient records. The
  antidote is the **3-2-1 backup rule** (3 copies, 2 media types, 1 offline/
  offsite) with **restores tested monthly**, plus a plan practised beforehand.

### International (well-documented)

- **WannaCry, 2017.** Ransomware that disrupted the UK's NHS, forcing cancelled
  operations. It spread on unpatched systems — preparation and patching (Modules
  2 & 4) are incident response that happens *before* the incident.
- **NotPetya, 2017 (Maersk, ~US$300M).** Destructive wiper masquerading as
  ransomware; survival hinged on a single surviving backup. Tested recovery is the
  difference between a bad quarter and the end of a business.
- **Colonial Pipeline, 2021.** The *decision* to shut operational systems — a
  containment judgement call — had national consequences. Response is as much
  disciplined decision-making as it is technical work.

## 7. Why it matters

- Evidence not preserved properly is worthless exactly when it matters most — in
  court, with the CSA/DPC, or in an insurance claim.
- Recovering deleted files and decoding artefacts is often how you learn what the
  attacker actually did and took.
- Following the lifecycle keeps a panicked response from destroying evidence or
  reinfecting clean systems.

## 8. Common mistakes

- **Powering off to "stop the attack"** — you destroy RAM evidence; isolate from
  the network instead.
- **Working on the original** — always image and hash first; analyse the copy.
- **Skipping the hash** — without before/after hashes you cannot prove integrity.
- **Containment that wipes evidence** — stop the spread, but preserve the scene.
- **Backups on the same network** — ransomware encrypts those too; you need an
  offline copy.

## Key takeaways

- **Hash before and after** — mathematical proof the evidence is unchanged;
  **Locard** guarantees the traces exist.
- **Order of volatility (RFC 3227): memory first**, disk later — never just power
  off.
- "Deleted" ≠ gone; `tsk_recover`/`icat` carve files back.
- **NIST SP 800-61 / PICERL**: Prepare → Detect → Contain → Eradicate → Recover →
  Post-Incident.
- **3-2-1 backups, tested monthly** — the control that decides whether you
  recover.

## Check yourself

1. **You reach a compromised server that's still running. Your instinct is to pull
   the power. Why is that wrong, and what do you do instead?**
   → Powering off destroys volatile memory evidence (processes, injected code,
   keys). Isolate from the network instead, then capture RAM before disk.

2. **Hashes match before and after analysis. What has that proven?**
   → That your analysis did not alter the evidence — its integrity and your chain
   of custody hold.

3. **`fls` shows a file marked `*`. What does that mean, and can you read it?**
   → It's deleted; yes — the data usually persists, so `icat`/`tsk_recover` can
   recover it.

4. **Containment vs eradication?**
   → Containment stops the spread (isolate) while preserving evidence; eradication
   removes the attacker (close the vector, reset credentials, remove persistence).

5. **The West African hospital's backups failed them. Why, and what rule fixes
   it?**
   → They were on the same network and got encrypted too. The 3-2-1 rule (one
   copy offline/offsite), with restores tested monthly, fixes it.

## Glossary

- **Locard's exchange principle** — every contact leaves a trace.
- **Hash (SHA-256)** — a file's cryptographic fingerprint.
- **Chain of custody** — the documented handling history of evidence.
- **Order of volatility (RFC 3227)** — collect the most perishable (RAM) first.
- **Autopsy / Sleuthkit / Volatility** — disk-forensics GUI / CLI / memory
  forensics.
- **inode** — a file's internal id in a filesystem.
- **NIST SP 800-61 / PICERL** — the incident-response lifecycle.
- **3-2-1 rule** — 3 copies, 2 media, 1 offsite/offline.
