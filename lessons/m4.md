# Module 4 — Vulnerability Management & SOC Operations

**Day 2 · Afternoon Session · ~4 hours · Hands-on lab: `labctl start m4`**

Finding weaknesses is the easy part — a scanner hands you hundreds in minutes.
The *profession* is deciding which handful actually matter, fixing those first
with a defensible rationale, and then — from a flood of thousands of daily alerts
— recognising the exact moment one of those weaknesses is being exploited and
acting before it becomes a breach. This module covers both halves of that
discipline: **vulnerability management** (the engine that keeps your exposure
shrinking) and the **Security Operations Centre** (the eyes that catch the attack
in progress).

As always the module runs on two registers. The **conceptual** half gives you
the prioritisation model (CVSS, KEV, EPSS, context), the SOC operating model
(tiers, SIEM/SOAR, MTTD/MTTR) and the single skill that separates a real analyst
from an alert-clicker: **correlation**. The **practical** half puts the tools in
your hands — fingerprinting and scanning a web server, discovering hidden
content, looting and cracking a leaked password database, demonstrating why a
weak credential falls in seconds, and triaging a realistic alert feed into one
coherent attack story. The attacks are taught for one reason only: you cannot
defend against, or prioritise, a threat you do not understand.

::: outcome | By the end of this module you will be able to
1. Run the vulnerability-management **loop** — discover → prioritise → remediate → verify → repeat — as an ongoing process, not a one-off scan.
2. Prioritise findings using **CVSS + CISA KEV + EPSS + context**, and justify why context can outrank a higher raw score.
3. Fingerprint and assess a web server with **nmap / whatweb / Nikto**, and discover hidden content with **gobuster**.
4. Recognise insecure credential storage (**unsalted MD5**) and explain why salting and slow hashes (bcrypt/argon2) defeat cracking.
5. Distinguish **online** password attacks (**Hydra**) from **offline** hash cracking (**hashcat / John**), and name the controls that defeat each.
6. Describe the SOC operating model — **Tier 1/2/3**, **SIEM/SOAR**, **MTTD/MTTR** — and triage alerts as **TP / FP / needs-investigation**.
7. **Correlate** multiple alerts by shared indicator into a single intrusion narrative, and tell whether the attacker succeeded.
8. Map the chain to **MITRE ATT&CK**: Brute Force (**T1110**), Valid Accounts, Privilege Escalation, Persistence via scheduled task/cron (**T1053**).
9. Produce a **remediation register** and a **SOC case ticket** of professional quality.
:::

Scanning (discover) is trivial and mostly automated. *Verify* — confirming the
fix actually closed the hole and did not break something else — is the step
beginners skip and auditors pound. But the hard, valuable, career-defining work
is **prioritise**, because you can never fix everything at once and pretending
otherwise paralyses the team.

### 1.2 Four inputs to a defensible priority

A priority you can defend to a CFO combines four things:

| Input | What it tells you | Limitation |
|-------|-------------------|------------|
| **CVSS** (0–10) | The *severity* of the flaw in the abstract | Describes the flaw, not **your** exposure |
| **CISA KEV** | Whether it is being **actively exploited right now** | Binary; a catalogue, not a score |
| **EPSS** (0–1) | *Probability* of exploitation in the next 30 days | Prediction, for the long tail not yet in KEV |
| **Context** | Internet-facing? critical asset? actually reachable? | Only *you* know this — it is your edge |

::: key | Context beats the raw number
A **medium-CVSS** flaw that is **internet-facing**, on a **critical system**, and
**listed in KEV** beats a "critical" CVSS flaw that is internal, unreachable and
never exploited. The scanner ranks by CVSS; the analyst re-ranks by *exposure and
exploitation*. That re-ranking is the job.
:::

## 2 · Web Assessment in Practice

Most organisations' worst exposure is a web server nobody is watching. The
assessment flow moves from *what is it* to *what is wrong with it* to *what can I
take*.

```Terminal — fingerprint, then scan the web server
# What software and version? (two ways)
nmap -sV -p80 10.13.4.10
whatweb http://10.13.4.10

# Web-specific vulnerability scan: dangerous files, stale software, headers
nikto -h http://10.13.4.10
```

Where Nmap says *port 80 is open*, **Nikto** says *what is wrong with what's
running on it* — a leftover `config.php.bak`, an exposed `/admin/`, a
`phpinfo.php` spilling internals, missing security headers.

### 2.1 Content discovery — finding what isn't linked

The most damaging files are the ones no link points to: a forgotten backup, an
admin console, a `.git` folder. **gobuster** brute-forces paths against a
wordlist to surface them:

```Terminal — discover hidden paths and loot a leaked backup
gobuster dir -u http://10.13.4.10 -w /usr/share/wordlists/dirb/common.txt

# directory listing left on → a world-readable database backup
curl http://10.13.4.10/backup/
curl http://10.13.4.10/backup/db_dump.sql -o db_dump.sql

# a leftover config backup leaks the live DB password in cleartext
curl http://10.13.4.10/config.php.bak
```

A world-readable `db_dump.sql` and a `config.php.bak` leaking the database
password are not hypothetical — they are among the most common real findings on
Ghanaian web estates, usually left by a hurried deployment or a "temporary"
backup that became permanent.

## 3 · Password Attacks — and Why Controls Are Mandatory

Here is the uncomfortable core of the module. We crack passwords **not to teach
hacking** but to prove, viscerally, why specific controls are non-negotiable. A
password already in a wordlist is already broken; the only question is how fast.

### 3.1 How passwords should (and shouldn't) be stored

Systems must never store passwords in plaintext. They store a **hash** — a
one-way fingerprint. But not all hashing is equal:

- **Unsalted MD5 / SHA1** — fast and identical for identical passwords. Two users
  with password `123456` have the *same* hash, and attackers precompute billions
  of these. This is **broken**; a 32-hex-character value (`-m 0` in hashcat) is
  your tell.
- **Salted, slow hashes (bcrypt, scrypt, argon2)** — a unique random *salt* per
  password defeats precomputation, and deliberate slowness makes mass cracking
  uneconomic. This is the standard.

### 3.2 Two kinds of attack, two kinds of defence

- **Online — Hydra.** Guessing against a *live* service (SSH, a web login). Noisy,
  rate-limited, and defeatable by lockout, throttling and MFA — but lethal against
  weak passwords. A **password spray** tries *one* common password across *many*
  accounts to slip under lockout thresholds.
- **Offline — hashcat / John the Ripper.** Cracking *stolen hashes* locally, at
  enormous speed, with **no lockout and no limit**. This is why a stolen hash
  database is a catastrophe, and why the storage choice in §3.1 matters so much.

```Terminal — online guessing (Hydra) vs offline cracking (hashcat / John)
# ONLINE: guess SSH credentials against the authorised lab host
hydra -l labuser -P assets/lab-wordlist.txt ssh://10.13.4.20

# OFFLINE: crack the looted unsalted-MD5 hashes (either tool)
hashcat -m 0 -a 0 hashes.txt assets/lab-wordlist.txt
john --format=raw-md5 --wordlist=assets/lab-wordlist.txt hashes.txt
john --show --format=raw-md5 hashes.txt
```

::: key | The control that makes a cracked password harmless
A cracked or stolen password is bad; **multi-factor authentication** is what makes
it *insufficient on its own*. Combine **strong, salted hashing** (so a stolen
database is slow to crack), **lockout/throttling** (so online guessing fails) and
**phishing-resistant MFA** (so a known password still cannot log in). Colonial
Pipeline fell because one of these — MFA — was missing on one account.
:::

## 4 · The SOC and Alert Triage

The **Security Operations Centre** is the team (or the one on-call person) that
watches the alerts. It is usually tiered: **Tier 1** triages and escalates,
**Tier 2** investigates, **Tier 3** hunts and handles the hard cases. Their core
skill is **triage** — for each alert decide **True Positive / False Positive /
Needs Investigation**, and escalate what matters.

The tooling: a **SIEM** (Security Information and Event Management, e.g. Wazuh,
Splunk) aggregates logs from across the estate and raises alerts against rules;
**SOAR** automates the repetitive response (enrich, block, ticket). Two metrics
govern effectiveness and appear in every board pack: **MTTD** (mean time to
detect) and **MTTR** (mean time to respond). Lower is better; both are the
difference between an incident and a breach.

::: warning | The real enemy is alert fatigue
A busy SIEM throws thousands of low-value alerts a day. A tired analyst starts
closing them to clear the queue — and that is *precisely* when the real attack
slips past, dressed as one more "failed login". Volume is not noise to be
dismissed; **volume is itself a signal**. Many low-severity alerts from one
source can be a single high-severity attack.
:::

## 5 · Correlation — The Master Skill

Ten alerts are rarely ten problems. They are usually **one attack seen from ten
angles**. Correlation is the discipline of linking alerts by a shared indicator —
most often a **source IP** — into a single narrative, and then asking the only
question that matters: *did it work?*

In this course you triage a realistic **Wazuh** alert feed (a JSON file) with
`jq`, rather than stand up a full SIEM — the deployment needs far more RAM than a
classroom laptop has, but the *skill* is identical.

```Terminal — correlate a Wazuh feed with jq
# Rank alerts by severity to see what matters
jq -r '.[] | "\(.rule.level)\t\(.rule.description)"' assets/wazuh-alerts.json | sort -rn | head

# Which source IP appears most? (the thread that ties the story together)
jq -r '.[].data.srcip // empty' assets/wazuh-alerts.json | sort | uniq -c | sort -rn

# What is the single highest severity firing?
jq '[.[].rule.level] | max' assets/wazuh-alerts.json
```

Read the output as a timeline. Dozens of **failed SSH logins** from one IP (brute
force, ATT&CK **T1110**) → a **web scan** from the *same* IP → an
**authentication SUCCESS** from that IP → a **sudo to root** → a **new cron job
created as root** (persistence, ATT&CK **T1053**). Individually: noise.
Correlated by that shared source IP: a brute-force that **succeeded**, escalated
to admin, and established persistence. That is the difference between "we had
alerts" and "we caught the intrusion".

## 6 · Mapping the Chain to MITRE ATT&CK

| Stage | What happened | ATT&CK technique |
|-------|---------------|------------------|
| Reconnaissance | Web fingerprint + content discovery | T1595 Active Scanning |
| Credential Access | SSH brute force / password spray | **T1110** Brute Force |
| Credential Access | Cracking looted unsalted-MD5 hashes | T1110.002 Password Cracking |
| Initial Access / Persistence of access | Logging in with a cracked/valid account | T1078 Valid Accounts |
| Privilege Escalation | Gaining root | TA0004 (e.g. T1548) |
| Persistence | New root cron job | **T1053.003** Scheduled Task/Job: Cron |

## 7 · Scenarios — The Unpatched Flaw and the Weak Credential

::: ghana | Ghana & West Africa
At 02:00 a SOC analyst at a Ghanaian bank sees dozens of low-severity "failed SSH
login" alerts — trivially easy to wave through when tired. But **one source IP is
behind all of them**, and minutes later there is an "authentication success" from
that same IP, then a "sudo to root", then a new cron job. Individually: noise.
**Correlated: a brute force that succeeded and escalated to admin.** The breached
institutions almost always *had* the alerts — they simply did not correlate them
in time. The same pattern drives MoMo-agent account takeovers across the region.
:::

::: case | Equifax, 2017 — 147 million people
The breach exploited **CVE-2017-5638** in Apache Struts — a vulnerability with a
patch available for **months** before the attack. A functioning
vulnerability-management loop (discover → prioritise → remediate → **verify**)
would have closed it. This is the price of a broken loop, and why *verify* is not
optional.
:::

::: case | Colonial Pipeline, 2021 — fuel to the US east coast halted
Ransomware entered through a **single reused VPN password with no MFA**. Not an
exotic zero-day — a credential-and-MFA failure, exactly the threat Hydra and John
exist to make you take seriously. One missing control on one account stopped a
pipeline.
:::

## 8 · The Worked Investigation (what the lab asks of you)

`labctl start m4` gives you a **leaky Apache web server** (`10.13.4.10`) and an
**SSH host with a weak account** (`10.13.4.20`), plus a looted hash file and a
realistic **Wazuh** alert feed. Work it end to end:

1. **Assess the web server** — fingerprint it (Apache), discover the exposed
   `/admin/` path with gobuster, and loot the world-readable `db_dump.sql` and the
   `config.php.bak` that leaks the **database password**.
2. **Crack the loot** — recognise the storage weakness (**unsalted MD5**), extract
   the `admin` hash, and crack it to plaintext with hashcat/John. Crack the
   `backup` account too, and demonstrate Hydra recovering the SSH password.
3. **Triage the SOC feed** — with `jq`, find the **source IP** behind both the
   brute force and the web scan, the **highest Wazuh rule level**, whether the
   attacker **got in**, and how they established **persistence** (the root cron
   job → T1053).

::: warning | Your values are unique
The admin password (and therefore its MD5 hash) and the leaked database password
are **randomised per student**; the examples here are illustrative. Crack and
report *your own* values — `labctl verify m4` grades against your personal answer
key, so a classmate's plaintext will fail.
:::

Then write the two deliverables: a **remediation register** that prioritises by
CVSS + KEV + exposure + criticality, and a **SOC case ticket** that correlates the
alerts into one incident with its ATT&CK mapping. Use `labctl worksheet m4`.

## Common mistakes

::: warning | What trips students up
- **Chasing CVSS alone.** A 9.8 nobody can reach matters less than a 6.5 on your
  internet-facing payroll box that is in KEV.
- **Skipping *verify*.** "Patched" without confirmation is how Equifax-shaped
  holes stay open.
- **Running Hydra/John/hashcat outside the lab.** Only the authorised targets and
  the provided hashes — anywhere else is an offence under Act 1038.
- **Closing alerts to clear the queue.** "Resolved" without investigation is where
  breaches hide.
- **Dismissing a low-severity flood.** Volume from one source *is* the signal.
- **Reporting alerts, not an incident.** The deliverable is the correlated story,
  not a list.
:::

## Key takeaways

::: key | Carry these out of Module 4
- Vulnerability management is a **loop** — discover → prioritise → remediate →
  **verify** → repeat.
- Prioritise by **CVSS + KEV + EPSS + context**; context and active exploitation
  outrank the raw score.
- Web assessment: **nmap/whatweb → Nikto → gobuster → loot**; forgotten backups
  and `*.bak` configs are the classic finding.
- **Unsalted MD5 is broken;** salt + slow hashes + **MFA** are the fixes. **Hydra**
  = online guessing; **hashcat/John** = offline cracking.
- SOC = **Tier 1/2/3 + SIEM/SOAR**; watch **MTTD/MTTR**; beware **alert fatigue**.
- **Correlation** by shared indicator turns ten alerts into one incident. ATT&CK:
  **T1110** (brute force), **T1053** (cron persistence).
:::

## Check yourself

1. **CVSS 9.1 on an internal test box (not in KEV) vs CVSS 6.8 on your public
   payment portal, listed in KEV. Which first, and why?**
   → The 6.8 — internet-facing, critical asset, and *actively exploited* (KEV).
   Context and exploitation beat the raw score.

2. **What does CISA KEV tell you that CVSS does not?**
   → Whether the vulnerability is being *actively exploited in the wild right
   now* — turning a theoretical score into a present threat.

3. **Hydra vs hashcat/John — the core difference, and the defence against each?**
   → Hydra guesses against a *live* service (online, rate-limited) — defeated by
   lockout/throttling + MFA. hashcat/John crack *stolen hashes* offline (no
   lockout, very fast) — defeated by salting + slow hashes.

4. **Failed logins, a web scan and a successful login — all from 10.13.4.66. How
   many incidents, and what's the skill?**
   → One incident — a successful intrusion. The skill is **correlation** by shared
   indicator (the source IP).

5. **A cracked password is bad; what single control makes it insufficient alone?**
   → Phishing-resistant **MFA**.

6. **Why do we deliberately store the lab's passwords as unsalted MD5?**
   → To let you *see* why it is broken — identical passwords share a hash and are
   precomputed/cracked in seconds; the fix is per-password salt + a slow hash.

## Glossary

- **CVE / CVSS** — a vulnerability's catalogue id / its 0–10 severity score.
- **CISA KEV** — the catalogue of vulnerabilities known to be actively exploited.
- **EPSS** — predicted probability a CVE will be exploited in the next 30 days.
- **Nikto / whatweb / gobuster** — web-vuln scanner / web fingerprinter / content brute-forcer.
- **Hash / salt** — a password's one-way fingerprint / per-password randomness that defeats precomputation.
- **Unsalted MD5** — a fast, broken storage scheme; `-m 0` in hashcat.
- **Hydra / hashcat / John** — online guesser / offline GPU cracker / offline CPU cracker.
- **SIEM / SOAR** — alert aggregation & rules / automated response.
- **MTTD / MTTR** — mean time to detect / to respond.
- **Triage / correlation** — classifying alerts / linking them into one incident.
- **KEV, cron persistence** — see ATT&CK **T1110**, **T1053.003**.
