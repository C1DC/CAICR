# Module 4 — Vulnerability Management & SOC Operations

**Day 2 · Afternoon Session · ~4 hours (the Day-2 defensive-operations deep dive) · Hands-on lab: `labctl start m4`**

Where Module 3 taught you to *break in*, Module 4 teaches you to run the two
functions that keep an organisation from being broken into — and to catch it the
moment someone tries. It stands on **two pillars**, each taught end to end with
real tools:

- **Vulnerability Management (VM)** — the engine that keeps your exposure
  shrinking: discover weaknesses across the whole estate (hosts, web, containers,
  cloud) with real scanners, *validate* which are genuinely exploitable, prioritise
  the handful that matter, and drive the fix to completion.
- **Security Operations (SOC)** — the eyes that catch the attack in progress: log
  sources and SIEM, alert triage, **correlation**, detection engineering, threat
  hunting and threat intelligence — measured by how fast you detect and respond.

Finding weaknesses is the easy part — a scanner hands you hundreds in minutes. The
*profession* is proving which are real, fixing the right ones first with a
defensible rationale, and then — from a flood of thousands of daily alerts —
recognising the exact moment one is being exploited and acting before it becomes a
breach. Both halves get equal, hands-on rigour.

The module runs on two registers. The **conceptual** half gives you the
prioritisation model (CVSS, KEV, EPSS, context), the SOC operating model (tiers,
SIEM/SOAR, MTTD/MTTR/dwell time) and the single skill that separates a real analyst
from an alert-clicker: **correlation**. The **practical** half puts the tools in
your hands — scanning with **OpenVAS/Nessus/nuclei/nmap**, validating with
**searchsploit, Metasploit and sqlmap**, scanning containers and cloud with
**Trivy/ScoutSuite**, then triaging a realistic SIEM feed, writing **Sigma/Wazuh**
detections, testing them with **Atomic Red Team**, and hunting with a hypothesis.

::: warning | The ethics line (same as Module 3)
This module uses real scanners and exploitation tools (Metasploit, sqlmap, nuclei,

own, or a sanctioned range. Scanning or exploiting anything else is an offence
under Ghana's **Cybersecurity Act, 2020 (Act 1038)** — *even "just to check".*

Scanning (discover) is trivial and mostly automated. *Verify* — confirming the
fix actually closed the hole and did not break something else — is the step
beginners skip and auditors pound. But the hard, valuable, career-defining work
is **prioritise**, because you can never fix everything at once and pretending
otherwise paralyses the team.

### 1.2 Four inputs to a defensible priority

Start from the distinction that trips up most teams: **CVSS measures the
*vulnerability's* severity in isolation — it does *not* measure *your* risk.** Your
risk is that severity filtered through *your* reality: is the asset internet-facing,
is there a compensating control, is the flaw actually being exploited (CISA KEV)?
A 9.8 on a box no one can reach is a smaller risk to you than a 6.5 on your public
portal that is in KEV. So a priority you can defend to a CFO combines four things:

| Input | What it tells you | Limitation |
|-------|-------------------|------------|
| **CVSS** (0–10) | The *severity* of the flaw in the abstract | Describes the flaw, not **your** exposure |
| **CISA KEV** | Whether it is being **actively exploited right now** | Binary; a catalogue, not a score |
| **EPSS** (0–1) | *Probability* of exploitation in the next 30 days | Prediction, for the long tail not yet in KEV |
| **Context** | Internet-facing? critical asset? actually reachable? | Only *you* know this — it is your edge |

::: key | Context beats the raw number
A **medium-CVSS** flaw that is **internet-facing**, on a **critical system**, and
**listed in KEV** beats a "critical" CVSS flaw that is internal, unreachable and
never exploited. The scanner ranks by CVSS; the analyst re-ranks by *exposure and
exploitation*. That re-ranking is the job.
:::

### 1.3 Read the CVSS vector, not just the number

"CVSS 9.8" is a conclusion; the **vector string** behind it tells you *why*, and a
professional reads it. CVSS v3.1 base score is built from eight metrics:

| Metric | Values | Asks |
|--------|--------|------|
| **AV** Attack Vector | Network / Adjacent / Local / Physical | How close must the attacker be? |
| **AC** Attack Complexity | Low / High | Does it "just work", or need special conditions? |
| **PR** Privileges Required | None / Low / High | Do they need an account first? |
| **UI** User Interaction | None / Required | Must a victim click something? |
| **S** Scope | Unchanged / Changed | Can it break out to other components? |
| **C / I / A** | High / Low / None | Impact on confidentiality / integrity / availability |

So `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` reads: *reachable over the
**network**, **low** complexity, **no** privileges or user interaction, full
impact on all three* → **9.8**. That is the profile of every internet-facing
unauthenticated RCE (Struts, the VPN appliance) — and it is why those top every
list. By contrast an `AV:L/PR:H/UI:R` flaw needs a local, privileged, tricked user
and scores far lower.

Three layers exist: **Base** (the flaw itself — what scanners report), **Temporal**
(is a working exploit public yet? is there a patch?), and **Environmental** (adjust
for *your* deployment). In practice, **KEV answers the temporal question** (it is
being exploited *now*) and **your context answers the environmental one** — which
is why the four-input model beats the base number alone.

### 1.5 Remediation that actually ships

Prioritising is half the loop; **getting the fix out** is the other. Professionals
run **patch SLAs by severity** — e.g. Critical/KEV within **24–72 hours** (an
*emergency change*), High within **7–30 days**, Medium within **90 days**, Low
best-effort — applied in agreed **maintenance windows**, with rollback ready.

When you *cannot* patch immediately (a legacy app, a vendor appliance, no window),
you deploy a **compensating control** to buy time: a **WAF virtual patch**,
**segmentation** to cut the attack path, disabling the vulnerable feature, or
tighter access control. Then — always — you **verify**: re-scan to confirm the
hole is closed and nothing else broke. A fix you didn't verify is a hope.

## 2 · Scanning the Estate — Finding the Weaknesses

"Discover" is the first step of the loop, and it is a discipline in its own right.
A real estate is hosts *and* web apps *and* containers *and* cloud — each with its
own scanner. Knowing which tool to point where, and how to read it, is the skill.

### 2.1 The scanner landscape — hosts and networks

A **vulnerability scanner** goes beyond Nmap's "what is open" to "what is
*wrong*": it fingerprints each service, matches it against a database of known
flaws (CVEs), checks configurations, and produces findings with CVSS scores. The
ones a professional knows:

| Tool | What it is | Use |
|------|-----------|-----|
| **OpenVAS / Greenbone** | The leading open-source vulnerability scanner | Full-estate authenticated/unauthenticated scans, free |
| **Nessus** (Tenable) | The commercial standard | Enterprise VM, deep plugin coverage |
| **`nmap --script vuln`** | Nmap's NSE vuln category | Quick, targeted check in the terminal |
| **nuclei** | Fast, template-driven scanner | Thousands of community YAML checks for known CVEs/misconfigs |
| **Qualys / Rapid7 InsightVM** | Cloud-delivered enterprise VM | Continuous scanning at scale |

```Terminal — host/network vulnerability scanning (lab scope only)
nmap -sV --script vuln 10.13.4.10               # NSE vuln scripts — quick triage
nuclei -u http://10.13.4.10                     # template-driven: CVEs, misconfigs, exposures
nuclei -l hosts.txt -severity critical,high     # many hosts, only what matters
# OpenVAS/Greenbone: run a "Full and fast" scan from the GUI (gvm-setup first) or:
gvm-cli ...                                      # drive it from the CLI in a pipeline
```

::: key | Authenticated scanning finds far more
An **unauthenticated** scan sees only what an outsider sees. An **authenticated**
scan (you give the scanner credentials) logs into each host and reads installed
patch levels — it finds the missing updates an external scan never could. Mature
VM programmes scan **authenticated**; the gap between the two is a useful measure
of how much an attacker learns *after* the first foothold.
:::

### 2.2 Web assessment in practice

Most organisations' worst exposure is a web server nobody is watching. The flow
moves from *what is it* → *what is wrong with it* → *what can I take*.

```Terminal — fingerprint, then scan the web server
# What software and version? (two ways)
nmap -sV -p80 10.13.4.10
whatweb http://10.13.4.10

# Web-specific vulnerability scan: dangerous files, stale software, headers
nikto -h http://10.13.4.10
# Deeper, modern web scanning:
nuclei -u http://10.13.4.10 -tags cve,exposure,misconfiguration
# OWASP ZAP (free) / Burp Suite — intercepting proxies + active scanners:
zaproxy -quickurl http://10.13.4.10 -quickout zap-report.html
```

Where Nmap says *port 80 is open*, **Nikto** says *what is wrong with what's
running on it* — a leftover `config.php.bak`, an exposed `/admin/`, a
`phpinfo.php` spilling internals, missing security headers. **OWASP ZAP** and
**Burp Suite** go further: they sit as a proxy between your browser and the app,
let you inspect and tamper with every request, and actively scan for the OWASP
Top 10 (the same classes you exploited by hand in the Juice Shop arena).

### 2.3 Content discovery — finding what isn't linked

The most damaging files are the ones no link points to: a forgotten backup, an
admin console, a `.git` folder. **gobuster** brute-forces paths against a
wordlist to surface them:

```Terminal — discover hidden paths and loot a leaked backup
gobuster dir -u http://10.13.4.10 -w /usr/share/wordlists/dirb/common.txt

# directory listing left on → a world-readable database backup
curl http://10.13.4.10/backup/
curl http://10.13.4.10/backup/db_dump.sql -o db_dump.sql

# a leftover config backup leaks the live DB password in cleartext
curl http://10.13.4.10/config.php.bak
```

A world-readable `db_dump.sql` and a `config.php.bak` leaking the database
password are not hypothetical — they are among the most common real findings on
Ghanaian web estates, usually left by a hurried deployment or a "temporary"
backup that became permanent.

### 2.4 Containers, dependencies & the cloud

The modern attack surface is not just servers. Applications ship as **containers**
built from layers of open-source packages, and run in **cloud** accounts whose
misconfiguration is now the *leading* cause of large breaches. VM must cover both.

- **Dependencies & containers:** a single vulnerable library (Log4Shell, 2021)
  exposed millions of apps — the flaw was in a *dependency*, not code anyone wrote.
  **Software Composition Analysis (SCA)** and image scanners find these.
- **Cloud posture:** public storage buckets, security groups open to `0.0.0.0/0`,
  over-permissive IAM. **Cloud Security Posture Management (CSPM)** tools audit it.

```Terminal — scan images, dependencies and cloud
trivy image nginx:1.18                     # CVEs in a container image, layer by layer
trivy fs --scanners vuln,secret,misconfig .   # scan a repo: vulnerable deps, leaked secrets, IaC misconfig
grype myapp:latest                         # alternative image/SBOM scanner
prowler aws                                # audit an AWS account against hundreds of checks (CSPM)
scoutsuite aws                             # multi-cloud posture report
```

External attack-surface management uses the same **Shodan/Censys** you met in the
resources list to find what the *internet* can already see of you — before an
attacker does.

## 3 · Validating Findings — Exploitation

A scanner finding is a **hypothesis**, not a fact. Scanners produce false
positives (a back-ported patch the version string doesn't show) and false
negatives, and they cannot tell whether a flaw is *reachable* in your deployment.
**Validation** — safely proving a finding is genuinely exploitable — is what turns
a 500-line scan report into a short list of *proven* risks a CFO will fund. It is
also the step that tells patch-weary engineers "this one is real, do it now."

**searchsploit** is an offline mirror of Exploit-DB — find whether a public
exploit exists for the exact software/version you found:

```Terminal — is there a known exploit? (then study it)
searchsploit apache 2.4.49                 # search by product + version
searchsploit -m 50383                      # copy a PoC locally to read/understand
```

**Metasploit** is the framework for validating and demonstrating exploitation. The
disciplined move is `check` — it verifies the target is exploitable **without**
firing the payload:

```Terminal — Metasploit: validate safely (lab / sanctioned only)
msfconsole -q
msf6 > search type:exploit struts
msf6 > use exploit/multi/http/struts2_...
msf6 > set RHOSTS 10.13.4.10
msf6 > set LHOST  10.13.4.2
msf6 > check                 # ← verify exploitable WITHOUT exploiting (prefer this for VM)
msf6 > run                   # only in an authorised test, in a maintenance window
```

**sqlmap** proves an injection you suspect (the JS-lab vulnerability class) and
shows its real impact — extracting the database — which is what makes leadership
act:

```Terminal — prove SQL injection end to end
sqlmap -u "http://10.13.4.10/item?id=1" --batch --dbs      # confirm + list databases
sqlmap -u "http://10.13.4.10/item?id=1" --batch -D app --tables --dump   # prove impact
```

::: warning | Validation can break things — treat it as a controlled act
Exploitation can crash a service or corrupt data. In a VM programme you prefer
**`check`**, PoCs you've read, and non-destructive confirmation; you run live
exploits only **with written authorisation, in a maintenance window, with the
owner informed and rollback ready.** In this course: lab targets only. This is the
line between a professional penetration test and a crime (Act 1038).
:::

## 4 · Secure Credential Storage — and Why Controls Are Mandatory

Credentials are the master key, and how they are *stored* decides whether a stolen
database is a minor scare or a national headline. (The full offensive
cracking craft — hydra, John, hashcat modes, rules, masks, spraying — lives in
**Module 3 §8**; here we focus on the storage decision that is VM's responsibility,
and prove, viscerally, why it matters.)

### 4.1 How passwords should (and shouldn't) be stored

Systems must never store passwords in plaintext. They store a **hash** — a
one-way fingerprint. But not all hashing is equal:

- **Unsalted MD5 / SHA1** — fast and identical for identical passwords. Two users
  with password `123456` have the *same* hash, and attackers precompute billions
  of these. This is **broken**; a 32-hex-character value (`-m 0` in hashcat) is
  your tell.
- **Salted, slow hashes (bcrypt, scrypt, argon2)** — a unique random *salt* per
  password defeats precomputation, and deliberate slowness makes mass cracking
  uneconomic. This is the standard.

### 4.2 Two kinds of attack, two kinds of defence

- **Online — Hydra.** Guessing against a *live* service (SSH, a web login). Noisy,
  rate-limited, and defeatable by lockout, throttling and MFA — but lethal against
  weak passwords. A **password spray** tries *one* common password across *many*
  accounts to slip under lockout thresholds.
- **Offline — hashcat / John the Ripper.** Cracking *stolen hashes* locally, at
  enormous speed, with **no lockout and no limit**. This is why a stolen hash
  database is a catastrophe, and why the storage choice in §3.1 matters so much.

```Terminal — online guessing (Hydra) vs offline cracking (hashcat / John)
# ONLINE: guess SSH credentials against the authorised lab host
hydra -l labuser -P assets/lab-wordlist.txt ssh://10.13.4.20

# OFFLINE: crack the looted unsalted-MD5 hashes (either tool)
hashcat -m 0 -a 0 hashes.txt assets/lab-wordlist.txt
john --format=raw-md5 --wordlist=assets/lab-wordlist.txt hashes.txt
john --show --format=raw-md5 hashes.txt
```

::: key | The control that makes a cracked password harmless
A cracked or stolen password is bad; **multi-factor authentication** is what makes
it *insufficient on its own*. Combine **strong, salted hashing** (so a stolen
database is slow to crack), **lockout/throttling** (so online guessing fails) and
**phishing-resistant MFA** (so a known password still cannot log in). Colonial
Pipeline fell because one of these — MFA — was missing on one account.
:::

### 4.3 Why slow hashing is the whole defence

For the lab you crack the looted hashes with the quick workflow below; the full
craft (`-m` modes, `-a` attacks, wordlists, rules, masks, spraying) is in **Module
3 §8** — don't duplicate it here, re-use it.

```Terminal — the lab cracking workflow (recap)
hashid hash.txt                                 # which algorithm? (unsalted MD5 = -m 0, 32 hex chars)
hashcat -m 0 -a 0 hashes.txt assets/lab-wordlist.txt   # straight wordlist
hashcat -m 0 hashes.txt --show                  # show cracked
```

::: key | Why the *storage* choice — not the password policy — protects a stolen database
A modern GPU tries **billions of MD5 guesses per second** — an unsalted-MD5
database falls in minutes, whatever your "complexity policy" said. The *same* GPU
manages only a few **thousand bcrypt guesses per second**, because bcrypt is
deliberately slow with a tunable *work factor* you raise as hardware improves.
**Salt** defeats precomputed (rainbow) tables; **slow hashing** (bcrypt/scrypt/
argon2) defeats brute force. This is VM's job to enforce: the day a database leaks
— and one day it will — the hashing decision you made years earlier is what
decides whether every account is instantly cracked or stays safe for years.
:::

## 5 · The SOC and Alert Triage

The **Security Operations Centre** is the team (or the one on-call person) that
watches the alerts. It is usually tiered: **Tier 1** triages and escalates,
**Tier 2** investigates, **Tier 3** hunts and handles the hard cases. Their core
skill is **triage** — for each alert decide **True Positive / False Positive /
Needs Investigation**, and escalate what matters.

The tooling: a **SIEM** (Security Information and Event Management, e.g. Wazuh,
Splunk) aggregates logs from across the estate and raises alerts against rules;
**SOAR** automates the repetitive response (enrich, block, ticket). Two metrics
govern effectiveness and appear in every board pack: **MTTD** (mean time to
detect) and **MTTR** (mean time to respond). Lower is better; both are the
difference between an incident and a breach.

::: warning | The real enemy is alert fatigue
A busy SIEM throws thousands of low-value alerts a day. A tired analyst starts
closing them to clear the queue — and that is *precisely* when the real attack
slips past, dressed as one more "failed login". Volume is not noise to be
dismissed; **volume is itself a signal**. Many low-severity alerts from one
source can be a single high-severity attack.
:::

### 5.1 Log sources — you can only see what you collect

A SOC is only as good as its inputs. Every detection depends on a **log source**
actually recording the behaviour (Module 3's lesson: no DNS log → no DNS
detection). The core sources and what each catches:

| Source | Catches | Key events |
|--------|---------|-----------|
| **Endpoint / EDR + Sysmon** | process execution, injection, persistence | Sysmon 1/3/11/13 |
| **Authentication** | brute force, spray, lateral movement | Windows 4624/4625/4768/**4769**; Linux `auth.log` |
| **Firewall / NetFlow** | scanning, exfiltration, C2 | connection logs, flow records |
| **DNS** | ~90% of C2, domain generation | query logs |
| **Web / proxy** | web attacks, downloads, exfil | access logs, user-agents |
| **Cloud** | account takeover, misconfig abuse | AWS CloudTrail, Azure AD sign-ins |
| **IDS/NSM** | known-bad patterns, anomalies | Suricata alerts, Zeek logs |

Mapping your log sources against **MITRE ATT&CK** shows your *coverage* — and,
more usefully, your **blind spots**: techniques no source can see.

### 5.2 The SIEM landscape — same skill, different dialect

The SIEM aggregates those sources and runs detection logic. The leaders differ in
cost and query language, but the analyst skill transfers:

| SIEM | Note | Query language |
|------|------|----------------|
| **Wazuh** (this course) | free, open-source, XML rules | rule groups / `jq` on the JSON |
| **Splunk** | the market standard | **SPL** |
| **Elastic / ELK** | open core, very common | KQL / EQL / Lucene |
| **Microsoft Sentinel** | cloud-native, Azure | **KQL** |

The *same* question — "which source IP has the most failed logins?" — in three
dialects:

```Terminal — one question, three SIEMs
# Splunk (SPL)
index=auth "Failed password" | stats count by src_ip | sort -count
# Sentinel / Elastic (KQL)
SecurityEvent | where EventID == 4625 | summarize count() by IpAddress | sort by count_ desc
# Wazuh in this course (jq on the alert JSON) — see §6
jq -r '.[].data.srcip // empty' assets/wazuh-alerts.json | sort | uniq -c | sort -rn
```

Learn the *thinking* (filter → group → rank → pivot) and you can work any SIEM;
the syntax is a lookup.

## 6 · Correlation — The Master Skill

Ten alerts are rarely ten problems. They are usually **one attack seen from ten
angles**. Correlation is the discipline of linking alerts by a shared indicator —
most often a **source IP** — into a single narrative, and then asking the only
question that matters: *did it work?*

In this course you triage a realistic **Wazuh** alert feed (a JSON file) with
`jq`, rather than stand up a full SIEM — the deployment needs far more RAM than a
classroom laptop has, but the *skill* is identical.

```Terminal — correlate a Wazuh feed with jq
# Rank alerts by severity to see what matters
jq -r '.[] | "\(.rule.level)\t\(.rule.description)"' assets/wazuh-alerts.json | sort -rn | head

# Which source IP appears most? (the thread that ties the story together)
jq -r '.[].data.srcip // empty' assets/wazuh-alerts.json | sort | uniq -c | sort -rn

# What is the single highest severity firing?
jq '[.[].rule.level] | max' assets/wazuh-alerts.json
```

Read the output as a timeline. Dozens of **failed SSH logins** from one IP (brute
force, ATT&CK **T1110**) → a **web scan** from the *same* IP → an
**authentication SUCCESS** from that IP → a **sudo to root** → a **new cron job
created as root** (persistence, ATT&CK **T1053**). Individually: noise.
Correlated by that shared source IP: a brute-force that **succeeded**, escalated
to admin, and established persistence. That is the difference between "we had
alerts" and "we caught the intrusion".

```Terminal — a few more jq patterns for triage
# Build a timeline: timestamp + rule for one source IP
jq -r '.[] | select(.data.srcip=="10.13.4.66") | "\(.timestamp)\t\(.rule.description)"' assets/wazuh-alerts.json | sort
# Only the high-severity alerts (level >= 10)
jq -r '.[] | select(.rule.level>=10) | .rule.description' assets/wazuh-alerts.json
# Did a success follow the failures from that IP? (the question that matters)
jq -r '.[] | select(.data.srcip=="10.13.4.66") | .rule.description' assets/wazuh-alerts.json | grep -i accept
```

## 7 · Detection Engineering — Catching It, Not Just Finding It

The SOC in §4 *triages* alerts; but a good alert doesn't appear by magic —
someone **engineers** it. Detection engineering is the discipline that turns "we
should catch brute-force-then-success" into a rule that fires reliably and rarely
cries wolf. The lifecycle:

**Use case → log source → rule → test → tune → document the response.**

You pick a behaviour worth catching (a use case), confirm the **log source**
actually shows it (no DNS log → no DNS detection, Module 3's lesson), write the
**rule**, **test** it against real attack traffic *and* a normal day, **tune** out
the false positives, and write the **response** so the Tier-1 analyst knows what to
do when it fires.

### 7.1 Detection as code — Sigma and Wazuh

Modern teams write detections as **code** so they are versioned and reviewed.
**Sigma** is a vendor-neutral rule format that *compiles* to Splunk, Elastic,
Wazuh and others — write once, deploy anywhere:

```Terminal — a Sigma rule for the brute-force → success chain (illustrative)
title: SSH brute force followed by a successful login (same source)
logsource: { product: linux, service: sshd }
detection:
  failed:  { message|contains: 'Failed password' }
  success: { message|contains: 'Accepted password' }
  timeframe: 10m
  condition: failed | count() by src_ip >= 20 and success by src_ip
level: high
```

The SIEM this course uses, **Wazuh**, expresses the same idea as a *composite* rule
that fires only when the pattern repeats from one source:

```Terminal — the equivalent Wazuh composite rule
<rule id="100120" level="12" frequency="8" timeframe="120">
  <if_matched_sid>5716</if_matched_sid>   <!-- 5716 = sshd authentication failed -->
  <same_source_ip/>
  <description>Possible SSH brute force: 8+ failures from one IP in 120s</description>
</rule>
```

### 7.2 Tuning, SOAR and hunting

- **Tuning.** A rule too noisy gets ignored (alert fatigue again); too narrow and
  it misses the attack. You **baseline** normal, **allow-list** known scanners and
  backup jobs, and set thresholds from real data — then review the rule's hit rate.
- **Aim up the Pyramid of Pain** (Module 1): a rule that matches the *behaviour*
  ("20 failures then a success from one IP") survives the attacker changing their
  IP; a rule that blocks one IP does not.
- **SOAR playbooks** automate the dull, fast parts: on this alert, auto-enrich
  (geo-locate the IP, check threat intel), auto-contain (block the IP, disable the
  account), and open a ticket — so humans spend their time on judgement, not
  copy-paste.
- **Threat hunting** is the proactive complement: *assume* a breach slipped past
  the rules and go looking with a hypothesis ("if an attacker were living off the
  land, I'd see unusual `sudo` from a service account") — findings become new
  detections.

::: key | A detection you haven't tuned and tested is decoration
The failure mode isn't too few rules — it's thousands of untuned rules nobody
trusts. Fewer, well-tuned, behaviour-based detections with a clear response beat a
wall of noisy ones every time. And none of it works without the **log source**:
detection engineering begins with logging the right thing.
:::

### 7.3 Testing your detections — purple teaming & Atomic Red Team

A detection you have never *triggered* is a hope, not a control. Mature teams
**test** detections the way developers test code: run the attacker technique in a
safe way and confirm the alert fires.

- **Atomic Red Team** — a free library of small, **ATT&CK-mapped** test scripts.
  Run one technique, check your SIEM lit up; if it didn't, your rule or log source
  has a gap.
- **ATT&CK Navigator** — a heat-map of the ATT&CK matrix where you shade the
  techniques you can detect. The white squares are your **blind spots** — the
  honest picture of coverage a board should see.
- **Purple teaming** — the red side executes, the blue side verifies detection and
  response, together, in one exercise. (Caldera and Atomic Red Team automate it.)

```Terminal — simulate a technique and confirm detection (lab / sanctioned only)
Invoke-AtomicTest T1053.005        # safely create a scheduled task (persistence)
# → then check: did your Sigma/Wazuh rule fire? If not, fix the rule or the log source.
```

::: key | Coverage you can prove beats coverage you assume
"We have 400 detection rules" is not an answer. "We tested our top-20 ATT&CK
techniques with Atomic Red Team last quarter and detect 17 of 20; here are the 3
gaps and the plan" is. Test, measure on the Navigator, close the gaps.
:::

## 8 · Threat Hunting & Threat Intelligence

Detection waits for a rule to fire. **Threat hunting** does the opposite: it
**assumes a breach already slipped past the rules** and goes looking, proactively
and hypothesis-first. It is how you find the dwell-time attacker who never tripped
an alert — and every hunt that finds something becomes a *new detection*.

**The hunt loop:** form a **hypothesis** ("if an attacker were living off the land,
a service account would show an interactive logon it never normally does") →
gather the data → analyse → if you find it, **turn it into a detection**; either
way, document what you checked so the next hunt starts further ahead.

Good hunts aim **up the Pyramid of Pain** (Module 1) — at *behaviours*, not
throwaway IOCs:

- unusual **parent-child** processes (Office → PowerShell → cmd);
- **LOLBins** reaching out to the internet (`certutil`, `rundll32` — Module 3);
- a **service account** with an interactive or remote logon;
- **beaconing** regularity in DNS/flow data;
- a **new local admin** or a new scheduled task across many hosts at once.

**Threat intelligence** feeds the hunt and the SIEM. It comes in three altitudes —
**strategic** (who targets our sector, and why), **operational** (campaigns and
TTPs), and **tactical** (concrete IOCs: hashes, domains, IPs) — and the practical
sources are ones you already met in the resources list:

| Source | What it gives | Use |
|--------|---------------|-----|
| **MISP** | a platform to store/share IOCs & events | the team's intel memory; feeds the SIEM |
| **AlienVault OTX / abuse.ch** | community IOC & malware feeds | auto-flag known-bad in the SIEM |
| **CISA KEV** | actively-exploited CVEs | drives VM prioritisation (§1) |
| **VirusTotal / GreyNoise** | file/URL verdicts / "targeted vs internet-noise" | enrich an alert during triage |

::: key | Intel ages — hunt the behaviour, not yesterday's IP
Tactical IOCs sit at the *bottom* of the Pyramid of Pain: an attacker changes a
domain or IP in seconds, so an IOC feed alone is always one step behind. Use IOCs
to **enrich and triage**, but **hunt and detect the TTP** — the behaviour the
attacker cannot easily change. That is what causes them real pain.
:::

## 9 · Mapping the Chain to MITRE ATT&CK

| Stage | What happened | ATT&CK technique |
|-------|---------------|------------------|
| Reconnaissance | Web fingerprint, content discovery, vuln scan | **T1595** Active Scanning; T1595.002 Vuln Scanning |
| Initial Access | Exploiting a validated public-facing flaw | **T1190** Exploit Public-Facing Application |
| Credential Access | SSH brute force / password spray | **T1110** Brute Force (T1110.003 Spraying) |
| Credential Access | Cracking looted unsalted-MD5 hashes | T1110.002 Password Cracking |
| Initial Access / Persistence of access | Logging in with a cracked/valid account | T1078 Valid Accounts |
| Privilege Escalation | Gaining root | TA0004 (e.g. T1548) |
| Persistence | New root cron job | **T1053.003** Scheduled Task/Job: Cron |

The attacker's job is to chain these; **yours** is to *detect* each one (a log
source + a tested rule — §5, §7) and to *prevent* the entry (a validated,
prioritised, verified fix — §1–§3). The ATT&CK Navigator is where you track which
of these you can actually see.

## 10 · Scenarios — The Unpatched Flaw and the Weak Credential

::: ghana | Ghana & West Africa
At 02:00 a SOC analyst at a Ghanaian bank sees dozens of low-severity "failed SSH
login" alerts — trivially easy to wave through when tired. But **one source IP is
behind all of them**, and minutes later there is an "authentication success" from
that same IP, then a "sudo to root", then a new cron job. Individually: noise.
**Correlated: a brute force that succeeded and escalated to admin.** The breached
institutions almost always *had* the alerts — they simply did not correlate them
in time. The same pattern drives MoMo-agent account takeovers across the region.
:::

::: case | Equifax, 2017 — 147 million people
The breach exploited **CVE-2017-5638** in Apache Struts — a vulnerability with a
patch available for **months** before the attack. A functioning
vulnerability-management loop (discover → prioritise → remediate → **verify**)
would have closed it. This is the price of a broken loop, and why *verify* is not
optional.
:::

::: case | Colonial Pipeline, 2021 — fuel to the US east coast halted
Ransomware entered through a **single reused VPN password with no MFA**. Not an
exotic zero-day — a credential-and-MFA failure, exactly the threat Hydra and John
exist to make you take seriously. One missing control on one account stopped a
pipeline.
:::

::: case | Log4Shell, 2021 — a flaw in a dependency, in everything at once
**CVE-2021-44228** was a critical RCE in **Log4j**, a logging library buried
*inside* thousands of products. Overnight, organisations discovered they were
vulnerable through software they didn't write and often didn't know they ran. It
is the textbook case for **§2.4**: you cannot patch what you cannot see, so VM must
inventory **dependencies and containers** (SCA/SBOM, Trivy), not just hosts — and
have a loop fast enough to respond when the whole industry is exposed on the same day.
:::

## 11 · The Worked Investigation (what the lab asks of you)

`labctl start m4` gives you a **leaky Apache web server** (`10.13.4.10`) and an
**SSH host with a weak account** (`10.13.4.20`), plus a looted hash file and a
realistic **Wazuh** alert feed. Work it end to end:

1. **Assess the web server** — fingerprint it (Apache), discover the exposed
   `/admin/` path with gobuster, and loot the world-readable `db_dump.sql` and the
   `config.php.bak` that leaks the **database password**.
2. **Crack the loot** — recognise the storage weakness (**unsalted MD5**), extract
   the `admin` hash, and crack it to plaintext with hashcat/John. Crack the
   `backup` account too, and demonstrate Hydra recovering the SSH password.
3. **Triage the SOC feed** — with `jq`, find the **source IP** behind both the
   brute force and the web scan, the **highest Wazuh rule level**, whether the
   attacker **got in**, and how they established **persistence** (the root cron
   job → T1053).

::: warning | Your values are unique
The admin password (and therefore its MD5 hash) and the leaked database password
are **randomised per student**; the examples here are illustrative. Crack and
report *your own* values — `labctl verify m4` grades against your personal answer
key, so a classmate's plaintext will fail.
:::

Then write the two deliverables: a **remediation register** that prioritises by
CVSS + KEV + exposure + criticality, and a **SOC case ticket** that correlates the
alerts into one incident with its ATT&CK mapping. Use `labctl worksheet m4`.

## Common mistakes

::: warning | What trips students up
- **Chasing CVSS alone.** A 9.8 nobody can reach matters less than a 6.5 on your
  internet-facing payroll box that is in KEV.
- **Reporting the raw scan.** A scanner finding is a *hypothesis* — **validate**
  it (searchsploit / `msf check` / sqlmap) before you make an engineer patch it.
- **Scanning only hosts.** The modern breach hides in a **dependency or cloud
  misconfig** (Log4Shell) — scan containers, dependencies and cloud too.
- **Unauthenticated-only scanning.** It sees the outside view; **authenticated**
  scans find the missing patches that matter after a foothold.
- **Skipping *verify*.** "Patched" without confirmation is how Equifax-shaped
  holes stay open.
- **Running Metasploit/sqlmap/Hydra/hashcat outside the lab.** Only the authorised
  targets and provided hashes — anywhere else is an offence under Act 1038.
- **Closing alerts to clear the queue.** "Resolved" without investigation is where
  breaches hide; and **volume from one source *is* the signal**.
- **Shipping untested detections.** A rule you never triggered (Atomic Red Team) is
  a hope; measure coverage on the ATT&CK Navigator.
- **Trusting an IOC feed as detection.** IOCs age in seconds — enrich with them, but
  hunt and detect the **behaviour** (TTP).
- **Reporting alerts, not an incident.** The deliverable is the correlated story,
  not a list.
:::

## Key takeaways

::: key | Carry these out of Module 4 — the two pillars
**Vulnerability Management**
- VM is a **loop** — discover → prioritise → remediate → **verify** → repeat —
  across hosts, web, **containers, dependencies and cloud** (Log4Shell lives there).
- **Scan with the real tools:** OpenVAS/Nessus/nuclei/`nmap --script vuln` (hosts),
  Nikto/ZAP/sqlmap (web), Trivy/Grype (deps/containers), Shodan/ScoutSuite
  (external/cloud). Scan **authenticated** to find what an outsider can't.
- **Validate before you escalate:** a scan finding is a hypothesis — prove it with
  **searchsploit / `msf check` / sqlmap** so you report *proven* risk.
- Prioritise by **CVSS + KEV + EPSS + context**; read the **vector** (AV:N/PR:N/UI:N
  = the 9.8 profile). Patch to an **SLA**; when you can't, use a **compensating
  control**; always **verify**.
- **Storage decides everything** when a DB leaks: salt + **slow hashing (bcrypt/
  argon2)** vs broken unsalted MD5. (Cracking craft → Module 3 §8.)

**Security Operations**
- SOC = **Tier 1/2/3 + SIEM/SOAR**; you can only detect what you **log** (map log
  sources to ATT&CK to find blind spots). Same skill across Wazuh/Splunk/Elastic/
  Sentinel — only the query dialect changes. Watch **MTTD/MTTR/dwell**; beware **alert fatigue**.
- **Correlation** turns ten alerts into one incident; **detection engineering**
  encodes it as a tuned, behaviour-based rule (Sigma/Wazuh) — and you **test** it
  (Atomic Red Team) and track coverage on the **ATT&CK Navigator**, with a SOAR response.
- **Hunt** proactively (assume breach, hypothesis-first, aim up the Pyramid of
  Pain) and enrich with **threat intel** (MISP/OTX/KEV) — but detect the **TTP**,
  not the expiring IOC.
- ATT&CK across the chain: **T1595** (scan), **T1190** (exploit public-facing),
  **T1110** (brute/spray), **T1078** (valid accounts), **T1053** (cron persistence).
:::

## Check yourself

1. **CVSS 9.1 on an internal test box (not in KEV) vs CVSS 6.8 on your public
   payment portal, listed in KEV. Which first, and why?**
   → The 6.8 — internet-facing, critical asset, and *actively exploited* (KEV).
   Context and exploitation beat the raw score.

2. **What does CISA KEV tell you that CVSS does not?**
   → Whether the vulnerability is being *actively exploited in the wild right
   now* — turning a theoretical score into a present threat.

3. **Hydra vs hashcat/John — the core difference, and the defence against each?**
   → Hydra guesses against a *live* service (online, rate-limited) — defeated by
   lockout/throttling + MFA. hashcat/John crack *stolen hashes* offline (no
   lockout, very fast) — defeated by salting + slow hashes.

4. **Failed logins, a web scan and a successful login — all from 10.13.4.66. How
   many incidents, and what's the skill?**
   → One incident — a successful intrusion. The skill is **correlation** by shared
   indicator (the source IP).

5. **A cracked password is bad; what single control makes it insufficient alone?**
   → Phishing-resistant **MFA**.

6. **Why do we deliberately store the lab's passwords as unsalted MD5?**
   → To let you *see* why it is broken — identical passwords share a hash and are
   precomputed/cracked in seconds; the fix is per-password salt + a slow hash.

7. **A finding's CVSS vector is `AV:N/AC:L/PR:N/UI:N/...C:H/I:H/A:H`. Why is that
   the worst-case profile?**
   → Reachable over the **network**, **low** complexity, **no** privileges and
   **no** user interaction, with full impact — an unauthenticated remote exploit
   anyone can run. That's the ~9.8 profile of Struts/VPN-style RCEs.

8. **Your brute-force rule fires 300 times a day, all false positives, so the team
   mutes it. What went wrong and how do you fix it?**
   → It wasn't **tuned** — baseline normal, allow-list known scanners/backup jobs,
   and raise the threshold to a real attack pattern (e.g. 20 failures *then a
   success* from one IP). An untuned rule is worse than none: it trains the team to
   ignore alerts.

9. **Your scanner reports a critical CVE on a server. Before you make the team
   patch it in an emergency change, what do you do and why?**
   → **Validate** it — check for a real exploit (searchsploit), confirm with
   `msf check` or a safe PoC, and confirm it's *reachable* in your deployment. You
   escalate *proven* risk, not a possible false positive.

10. **Why must a vulnerability-management programme scan containers and cloud, not
    just servers?**
    → The modern breach hides in a **dependency** (Log4Shell) or a **cloud
    misconfig** (public bucket, open security group). Trivy/Grype scan images and
    dependencies; ScoutSuite/Prowler audit cloud posture. You can't patch what you
    don't inventory.

11. **You have 400 detection rules. A board member asks "are we covered?" What's
    the professional answer?**
    → Not the count — the **tested coverage**: "we validated our top ATT&CK
    techniques with Atomic Red Team, detect N of M, and here are the gaps and the
    plan" — shown on the **ATT&CK Navigator**. Rules you've never triggered aren't coverage.

12. **Detection vs threat hunting — what's the difference, and why hunt?**
    → Detection waits for a rule to fire; **hunting assumes a breach already slipped
    past** and looks proactively, hypothesis-first, for behaviours (LOLBins, odd
    parent-child, service-account logons). It finds the dwell-time attacker no rule
    caught — and every find becomes a new detection.

## Glossary

- **CVE / CVSS** — a vulnerability's catalogue id / its 0–10 severity score.
- **CISA KEV** — the catalogue of vulnerabilities known to be actively exploited.
- **EPSS** — predicted probability a CVE will be exploited in the next 30 days.
- **Nikto / whatweb / gobuster** — web-vuln scanner / web fingerprinter / content brute-forcer.
- **Hash / salt** — a password's one-way fingerprint / per-password randomness that defeats precomputation.
- **Unsalted MD5** — a fast, broken storage scheme; `-m 0` in hashcat.
- **Hydra / hashcat / John** — online guesser / offline GPU cracker / offline CPU cracker.
- **CVSS vector** — the metric string (AV/AC/PR/UI/S/C/I/A) behind the score; base vs temporal vs environmental.
- **Patch SLA / compensating control** — the deadline to fix by severity / a stop-gap (WAF, segmentation) when you can't patch yet.
- **hashcat mode (`-m`) / attack (`-a`)** — which algorithm / which strategy (wordlist, rules, mask).
- **rockyou / potfile / rules** — a 14M-password wordlist / hashcat's store of cracked hashes / mutations applied to a wordlist.
- **SIEM / SOAR** — alert aggregation & rules / automated response (playbooks).
- **Detection engineering** — building and tuning the rules that generate good alerts (as code: Sigma, Wazuh).
- **Sigma** — a vendor-neutral detection-rule format that compiles to many SIEMs.
- **Threat hunting** — proactively searching for intrusions the rules missed, hypothesis-first.
- **MTTD / MTTR** — mean time to detect / to respond.
- **Triage / correlation** — classifying alerts / linking them into one incident.
- **OpenVAS / Greenbone / Nessus** — the leading open-source vulnerability scanner / its platform / the commercial standard.
- **nuclei** — a fast, template-driven scanner (community YAML checks for CVEs, misconfigs, exposures).
- **Authenticated vs unauthenticated scan** — logged-in (finds missing patches) vs outside-view scanning.
- **OWASP ZAP / Burp Suite** — intercepting proxies + active web scanners for the OWASP Top 10.
- **Validation / exploitation** — proving a scan finding is genuinely exploitable before escalating it.
- **searchsploit / Metasploit (`msfconsole`, `check`) / sqlmap** — offline Exploit-DB search / exploitation framework (`check` = verify without firing) / automated SQL-injection prover.
- **SCA / SBOM / Trivy / Grype** — software composition analysis / a bill of materials of dependencies / container & dependency scanners.
- **CSPM / ScoutSuite / Prowler** — cloud security posture management / multi-cloud and AWS posture auditors.
- **Log source** — a feed (EDR/Sysmon, auth, firewall, DNS, cloud) a detection depends on; no source → no detection.
- **SIEM dialects — SPL / KQL** — Splunk's query language / the language of Microsoft Sentinel and Elastic.
- **ATT&CK Navigator** — a heat-map of detection coverage across the ATT&CK matrix (white = blind spot).
- **Atomic Red Team / purple teaming** — ATT&CK-mapped tests to trigger and verify detections / red + blue validating together.
- **Threat intelligence (strategic/operational/tactical) / MISP / OTX** — knowledge of adversaries at three altitudes / an intel-sharing platform / AlienVault's open feed.
- **Dwell time** — how long an attacker stays undetected; the metric hunting attacks.
- **KEV, cron persistence** — see ATT&CK **T1110**, **T1053.003**.
